Launch a subagent: an autonomous child agent that takes one sub-task, works through it in its own context, and reports back to you once.

Two kinds of subagent run through this tool:
- Subagent: subagent_type "general", available only when general is in the list below; there, omitting subagent_type also gives you one. A general-purpose worker for any self-contained sub-task: broad research, multi-file search, implementation, refactors, or running and repairing checks.
- Subagent specialists: every other type in the list below. Each has a fixed focus and its own permissions. Choose one only when part of the work clearly matches its description, and use it proactively when its description says to.

When general is in the list, size the task before you start: count the files you will create or change, and the parts of the work that do not depend on each other. The task is big when it touches three or more files that fall into two or more independent parts, or when it needs broad research across the codebase as well as changes. The counts decide, not the size of each file: several quick files in independent modules still make a big task. For a big task you MUST launch general Subagents before you write those files yourself, without waiting to be asked:
- one per independent part (separate modules, packages, features or questions), all in ONE message, each with non-overlapping owned_paths;
- one for research that needs wide searching or reading that would flood your context;
then keep integration and final verification yourself.

When general is not in the list, or you are yourself a Subagent working on a brief, do not request general. Always set subagent_type to a listed specialist, use one only when part of the work clearly matches its focus, and do the rest yourself, big tasks included.

Do not launch a general Subagent for a small task; do it yourself:
- a single-file change or a quick fix, including a single-file edit that is faster to make than to describe;
- two or three closely coupled files that are parts of one unit, for example a type, its serializer and its test;
- one lookup: reading a file whose path you know, or finding one symbol or definition (use Read, Glob or Grep instead);
- a short answer or explanation, or a question about two or three known files;
- anything that needs back-and-forth with the user.

Usage notes:
1. Launch in parallel. Put every independent task call in ONE message: they run at the same time and their results come back together. Vector sets no limit, so launch as many as the work genuinely splits into. When that is more than a few, tell the user how many you launched, because each one spends on their provider keys.
2. Write a brief that stands alone. A subagent sees none of your conversation, so brief it as you would a capable engineer who is new to the task: the goal and why it matters, the relevant files and constraints, what you already know or have ruled out, whether to change code or only research, how to verify, and exactly what its final message must contain. Tell a subagent that edits code to stay inside its owned_paths and never revert changes it did not make.
3. description is the 3-5 word title the user sees on the subagent's card. Make each one specific and distinct from its siblings.
4. For parallel implementation, give each subagent non-overlapping owned_paths and concrete success_criteria. Use depends_on with earlier task IDs when one subagent's work must finish before another starts. Vector rejects overlapping ownership among active sibling subagents instead of letting them overwrite each other.
5. Once you delegate a piece, do not also do it yourself, and never sleep, poll, or ask a running subagent for status. Continue with non-overlapping work, or wait for the results.
6. The result comes back only to you; the user does not see it. Read it, integrate it, run the integration checks yourself, and summarize the outcome for the user. A subagent's report is evidence, not proof; use the judge specialist when you need an independent rubric-based verdict.
7. Each call starts a fresh subagent unless you pass task_id from an earlier result, which continues that same subagent session with its previous messages and tool outputs.

<example>
user: Remove every place we log user emails.
assistant: [general is in the list and the work spans three packages, so it sends ONE message with three task calls and no subagent_type: "Strip email logs: api" with owned_paths packages/api, "Strip email logs: worker" with owned_paths packages/worker, and "Strip email logs: web" with owned_paths packages/web. Each brief names the logger calls to look for, says to redact the email rather than delete the log line, and asks for the files changed plus the test command it ran and its result.]
<commentary>A big task that splits into three independent packages, so three Subagents launched together with non-overlapping ownership.</commentary>
</example>

<example>
user: Add slugify, formatMoney and retry helpers in src/utils, each with its own test file, and document them in the README.
assistant: [general is in the list. The request needs six new files in three independent modules plus a README section, so it is big. Before writing any of them it sends ONE message with three task calls and no subagent_type: "Add slugify helper" owning src/utils/slugify.ts and test/slugify.test.ts, "Add formatMoney helper" owning src/utils/money.ts and test/money.test.ts, and "Add retry helper" owning src/utils/retry.ts and test/retry.test.ts. Each brief gives the function signature, the edge cases to cover and the test command to run. When all three report back, it writes the README section from their results and runs the whole test suite itself.]
<commentary>Each file is quick on its own, but three independent modules with tests make a big task: one Subagent per module, launched together. The README depends on all three, so it waits for their results and stays with you, along with final verification.</commentary>
</example>
