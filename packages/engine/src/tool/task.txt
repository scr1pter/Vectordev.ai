Delegate one to eight complete briefs in tasks: [...]. Each child is autonomous, has its own context and reports back to you.

Use only the agent types listed below. Omit subagent_type for general, which can research, search, implement, refactor, and run or repair checks, only when general is listed. Name a specialist only for substantial work matching its description. When general is not in the list, or you are a Subagent working on a brief, name a listed specialist and never general, and do uncovered work yourself, even large tasks.

Do not delegate small fixes, single-file edits, two or three tightly coupled files, known-file or symbol lookups (use Read, Glob or Grep), short explanations or work needing back-and-forth with the user.

Execution rules:
1. Put every known independent brief within the user's request in one tasks array; do not split known parallel work across later responses. Vector checks the whole array and its permissions before starting any child, then runs the accepted entries concurrently and waits for their results. New entries run in the foreground; resume an active child only in a one-item array, which keeps its mode. Never mix tasks with top-level brief fields. Prefer fewer, substantial parts: each child spends the user's provider budget on its prompt and reading. Tell the user the count when launching more than a few.
2. Each prompt is a standalone brief: goal/rationale, files, constraints, known findings, rejected approaches, edit-versus-research scope, verification and final report. Editing children must stay within owned_paths and never revert others' changes.
3. Entries for parallel implementation need non-overlapping owned_paths and concrete success_criteria. depends_on takes only existing earlier task IDs, never another entry of the same array. Never repeat a task_id in an array.
4. Do not duplicate delegated work. Continue independent work or wait for results; never sleep, poll or ask a running child for status.
5. Results reach you, not the user. Use judge for an independent rubric-based verdict when needed.

Examples:
- Remove email logging across three packages with many call sites: use three general tasks together if available, one owner per package, preserve useful events through redaction, and require changes/tests in each report.
- Three small helpers plus tests/README, or a date fix in a known footer: inspect, edit and verify yourself; several files alone do not justify separate children.
- With general unavailable, use explore for substantial session-token research, then fix and verify expiry yourself.
