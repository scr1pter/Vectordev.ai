Maintain a structured list of substantial milestones when the user requests a todo list/tracked plan, work has several substantial independent objectives, or extended work needs checkpoints to prevent omissions and retain progress.

Unless explicitly requested, skip tracking for a single bounded objective (including multi-file mechanical changes), routine investigation/editing/verification, informational requests, or work where tracking adds no value. Multiple files or tool calls alone do not justify a list.

States: pending = not started; in_progress = actively working; completed = finished successfully; cancelled = no longer needed. Keep exactly one in_progress while work remains.

Rules:
- Use specific, actionable milestones, splitting large work into substantial outcomes rather than individual searches, reads, edits or test commands.
- Persist observed progress, new blockers and changed requirements before reporting final status; prose alone does not update the list. Combine known status changes and, when possible, independent productive calls in the same response.
- Mark completed only after work and required verification finish, never on intent. Keep the original blocked/partial milestone in_progress, including failed verification; add a pending follow-up describing the blocker rather than moving that milestone to pending.
- Preserve user commands verbatim, including flags, arguments and order.

Examples: track several complex features, a storage/API/import migration, or an explicitly requested bug-fix plan. Otherwise skip a request to fix one failing test without changing tests, a feature with verification, rename, comment edit, command or informational question.
