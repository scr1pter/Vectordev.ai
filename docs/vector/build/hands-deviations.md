# Vector Hands build: deviations from the contract

## 2026-10-28 E0 (shared schema files)

Smallest changes that keep the contract's intent; later packages should build on these shapes.

1. **`ComputerState` is an Effect Schema** (value and type of the same name), not a plain type. It crosses the bridge in `act` and `heartbeat` responses and becomes the `computer.state` bus event (E6b), so it needs decoding. The other desktop views (`ComputerPrefs`, `ComputerPolicy`, `ResolvedComputerSettings`, `ComputerPlatform`, `PermissionsView`, `AlwaysAllowed`) stay plain types; `PREFS_KEYS`, `POLICY_KEYS`, `SETTINGS_KEYS` and `PLATFORM_KEYS` give their keys at run time (compile-checked as complete) for the INV-T1 shape test.
2. **`ComputerApps.category(app, signals)`**: `signals` gains optional `windowClass`, because 2.3 keys the table by window class (ConsoleWindowClass, CASCADIA_HOSTING_WINDOW_CLASS, taskbar classes) but its signature only had `childShell`.
3. **`AppMatcher`** is one app (or family) per entry: `{key: "builtin:<slug>", name, category, macos?: bundleIds[], windows?: {aumid?, windowClass?, binary?}}`, ids case-insensitive, a trailing `*` matches by prefix. `TABLE` exports every entry (never categories first). `ComputerPrefs.unblocked` stores a DEFAULT_BLOCKED entry's `key`.
4. **`builtinRule`** also returns `key` and `name` (for Settings rows and the unblocked check). Added `builtinVerdict(app, {unblocked}, signals)` (the built-in layer of section 2.6 that D15's `access()` should call first), plus `matches`, `find`, `benign`, `isNever`. A DEFAULT_BLOCKED match reports `reason: "user"` (BlockReason has no `default`; the verdict uses `blocked: default`).
5. **System rule vs DEFAULT_BLOCKED.** Disk Utility, Find My and Migration Assistant are Apple platform binaries, so "system and not benign is security" would make them never and contradict 2.3/1.5 K ("removable", [Allow]). `category` therefore treats a system identity that matches DEFAULT_BLOCKED as its listed category. **Cross-package risk (C1, M6, W7):** the helpers' system deny must exempt the DEFAULT_BLOCKED system entries, or a user's [Allow] for them is refused with `protected` at the helper.
6. **BENIGN_SYSTEM** adds ordinary Apple apps under M6's "and similar": Reminders, Contacts, Messages, Maps, Music, TV, Podcasts, Books, Freeform, Stickies, QuickTime Player, Font Book, Dictionary, Weather, Clock, Chess, News, Stocks. FaceTime, Photo Booth, Voice Memos, Home and Journal are left out (calls, camera, microphone, home devices, private journal), so they stay `security`.
7. **Keychain Access** is `password-manager` (reason `passwords`, copy "can't use password managers or Keychain") rather than `security`; 2.3 names it under both and both are never.
8. **Bridge shapes left open by 2.8:** `acquire` returns `{lease}`, `{code: "busy", holder}` or `{code: "permissions", missing}` as 200 bodies; empty responses are `{ok: true}`; `AppQuery` is `{key}` or `{name}`; `openApp.app` also takes `{path}`; `act` takes 1 to 10 steps.
9. **Helper shapes left open by 2.10:** array results are wrapped (`displays.list` gives `{displays}`, `apps.list` gives `{apps}`) so a response stays `{id, ok: true, ...result}`; `cancel`'s argument is `target` because the frame envelope already uses `id`; request ids are non-negative integers; keyboard ops (`input.key`, `input.type`, `input.hold`) carry the `pid` the focused app must belong to instead of `captureId, x, y`; `input.hold` holds a key combo for `ms`; `permissions.request` and `permissions.reset` return the permission status; `app.activate`, `app.launch` and `window.focus` return `{foreground?}`. `HelperEvent` includes `exit`, which only desktop main's supervisor raises.
10. **`ComputerBackend.capture`** returns `bytes: Uint8Array` (the schema package is browser-safe; a Node Buffer satisfies it).
11. **`appKey`** escapes `%` and `|` inside Windows exe parts (`%25`, `%7c`) so two identities can never share a key; ordinary values are unchanged. An exe identity with `verified: false` keys as `unsigned` even if a publisher string is present. `parseAppKey` rejects keys that are not lowercase.
12. **Shared constants live in E0's modules:** `Computer.MENTION_KEY` (D1's `Hands.MARKER` should reuse it), `ComputerApps.VECTOR_APP_IDS`, `HELPER_SUFFIX` and `ELECTRON_HELPER_SUFFIXES` (D1's `helperBundleId` and C1's generator should reuse them), `Computer.LIMITS` (section 2.12 numbers), `Computer.BRIDGE`, `Computer.HELPER_CLI`.
13. **Display text** in ask metadata, part metadata, the mention marker and state rejects control and bidi characters; producers clean text with `Computer.clean(text, max)`.
14. **Not identifiable from identity alone (helpers must cover them):** the Windows Run dialog is matched by its window AUMID `Microsoft.Windows.Shell.RunDialog`, which only the helper can read (W7); Windows Credential Manager shown inside a Control Panel (explorer) window has no identity of its own (W7).
15. Tests live in `packages/core/test` as the contract says, although `packages/schema/test` exists and runs with bun.

## 2026-10-28 D1 (brand constant and naming guard)

1. **`hands.ts` has no imports.** `Hands.MARKER` and the helper bundle id suffix are written as literals instead of importing `Computer.MENTION_KEY` and `ComputerApps.HELPER_SUFFIX` (E0 note 12), so renderer, preload, overlay pages and main copy can read the brand file without loading the Effect schemas. `packages/core/test/hands-brand.test.ts` pins `Hands.MARKER === Computer.MENTION_KEY`, `helperBundleId(id) === \`${id}.${ComputerApps.HELPER_SUFFIX}\`` for every `VECTOR_APP_IDS` entry, and that the helper id is classified `vector` (never-listed).
2. **Extra exports:** `Hands.Channel` (`"prod" | "beta" | "dev"`, desktop main's channel names) and `Hands.CHANNELS`. `helperName` treats an unknown channel as dev, as desktop main's `CHANNEL` does. `Hands` is also in the schema root barrel, next to E0's `Computer` and `ComputerApps`.
3. **The guard is a superset of the contract:** it also reads `packages/ui/src` (a renderer surface package in 4.1, where D2 adds `ui.tool.computer.*`). It matches `Hands.NAME` case-sensitively with any whitespace, `&nbsp;`/`&#160;` or a written ` ` between the words, in code and comments alike ("Vector hands it to..." as a verb is not matched). Exempt: `packages/schema/src/hands.ts`, any file under an `i18n/` directory, `*.test.*`/`*.spec.*` files and files under `test/`, `tests/`, `__tests__/` or `e2e/`. Later packages (D2's `main-copy.ts`, D11's catalog blurb, D13 to D23's desktop main comments) must build the name from `Hands.NAME`, never write it.
4. `hands.ts` writes the name only in `NAME` (comments refer to NAME), and the guard test checks it appears there exactly once.

## 2026-10-28 E1 (permission policy)

1. **`canAlwaysApprove` for `computer_app` accepts only concrete app keys.** The contract's check is `always.every((p) => p.startsWith("app:"))`. The code also rejects the bare prefix `app:` and any pattern containing a wildcard character (`*` or `?`, the two `Wildcard.match` treats specially), so `app:*` or `app:macos:*` can never be saved as Always allow. This is stricter in the safe direction and keeps the contract's own cases (`["app:macos:com.apple.calculator"]` true, `["*"]` false). An app whose key really contains `*` or `?` simply gets no Always offer.
2. **Reason string values.** The contract names `AFTER_SCREEN_REASON` and `FLAGGED_SCREEN_REASON` without values. `AFTER_SCREEN_REASON` takes the engine design's value for the `new_destination` ask ("Text on your screen can steer the agent, and this address or recipient is new: you did not give it."); `FLAGGED_SCREEN_REASON` is the section 1.5 C reason line for flagged screen text. Neither names the feature, so `hands.ts` stays the only place the name is written.
3. **Gap until E2 (no ask is skipped, but INV-C5's "never kept" half belongs to E2).** Because `canAlwaysApprove` is now true for `computer_app` with app keys, an "always" reply is no longer downgraded to "once": the engine's `Permission.reply` pushes the pattern into its in-memory `approved` list, and `PermissionV2.reply` writes it to the saved table, where `savedRules` purges it on the next read (`isSensitiveAction` is true for every `computer_*`). Neither path can answer a computer ask, because `requiresApproval` is now true for every `computer_*` (the engine starts with `needsAsk = true`; V2 returns `ask` whatever the allow rules and saved approvals say, and both auto-resolve loops skip such requests). E2 removes the engine push ("skip approved.push for computer_*") and owns "V2 never saves computer_*"; the V2 save path (`reply === "always" && save.length` → `saved.add`) should also skip `computer_*` there rather than relying on the purge.

## 2026-10-28 E2 (ctx.ask returns the answer; the engine never persists a computer grant)

1. **New read accessor `Permission.Service.approved()`** (packages/engine/src/permission/index.ts), plus the exported type `Permission.Answer = "once" | "always"`. A `computer_*` entry in the in-memory approved list has no observable effect through `ask`/`reply`/`list`, because every `computer_*` request always asks and both auto-resolve loops skip it. So the INV-C5 test "an always reply to computer_app leaves approved empty" needs to read the list directly. Nothing outside the layer implements the interface, so no stubs change.
2. **A computer "always" answers only its own ask.** The contract says to skip `approved.push` for `computer_*`. `reply()` now returns right after resolving a `computer_*` request, so it also skips the same-session auto-resolve loop: an unrelated request that waited in that session stays the person's to answer. Non-computer "always" replies still push and run the loop, which resolves with "always". V2 does the same: `save = reply === "always" && save.length && !isSensitiveAction(action)`. It saves only when `save` is true, and it runs the follow-up loop only after a save. For every non-computer action this matches the old condition, because `canAlwaysApprove` true implies `canAutoApprove` true. Tests: "reply - an always reply to a computer permission answers only that ask" (engine) and the waiting-request block in "V2 never saves computer_*" (core).
3. **`isSensitiveAction` (core V2) already matched every `computer_*` id**, because `canAutoApprove` is false for the whole prefix. It was not extended; a comment now says so. The V2 save path now skips sensitive actions instead of relying on the purge in `savedRules`, as E1's note asked.
4. **The plugin bridge stays `Promise<void>`.** `packages/engine/src/tool/registry.ts` maps `toolCtx.ask(req)` through `Effect.asVoid` before handing it to a plugin, because `@vectordevai/plugin`'s `ToolContext.ask` returns `Promise<void>` and the wider type does not fit it. The plugin API is unchanged.
5. **Test harness.** "V2 never saves computer_*" uses an in-memory `PermissionSaved` replacement that records every `add`. Without it the test could not tell a write that the next `savedRules` read purges from no write at all: under the old code the post-save loop purges it within the same `reply`.

## 2026-10-28 E3 (agent defaults and plan-mode gating)

1. **Tool-list asks cover both kinds of tool-list agent.** The contract points at the research agents' block (374-376). The read-only specialists (explore, review, judge, security) also build their rulesets from a tool list, so both now spread `computerAsks(tools)`, a small function exported from `packages/engine/src/agent/agent.ts`. It returns the four `computer_*: "ask"` entries when the list includes `computer`, and nothing otherwise. No agent's list includes `computer` today (subagents never get the tool, INV-S10), so the function is exported for the test to check directly. Those agents keep denying every `computer_*` through their `"*": "deny"`.
2. **Plan mode's denies are applied last as well.** The contract adds `computer_interact: "deny"` and `computer_sensitive: "deny"` to the plan block, which merges before the user's rules. In this codebase user rules override plan mode's own rules (for example `task: {general: allow}`), so a user or trusted-repo `"*": "allow"`, or `agent.plan.permission.computer_interact: "allow"`, would have reopened them. The two denies stay in the plan block and are also applied after the config loop and the user ceiling, so no rule reopens them. `computer_app` still asks in plan mode. The `computer` tool itself stays offered, because `Permission.disabled` keys on the tool id and not on `computer_*`. E6 can therefore read plan mode's observe-only state from the ruleset (`Permission.evaluate("computer_interact", "*", ruleset).action === "deny"`) as well as from the agent name.
3. **No allow evaluates to allow for a `computer_*` permission (stricter, ruleset level).** After the config loop, a final pass puts an ask for the same pattern right after every allow rule that covers a computer permission. That covers `"*": "allow"`, `"computer*": "allow"` and named or pattern-specific allows, from user, repository and agent config. So the merged ruleset reads `ask` where the runtime asks anyway (`PermissionPolicy.requiresApproval`, E1), and a deny written after the allow still wins. A deny written before an allow now reads as `ask`; before this pass it read as `allow`. The tool id `computer` is not touched. Session-level rules, which are merged after agent rules at run time, are outside this pass. requiresApproval still makes them ask, and E6's refusal in plan mode is the authoritative check there.

## 2026-10-28 E4 (company-only computer config)

1. **Optional fields preserve managed-layer precedence.** `ConfigComputerV1.Info` follows the existing config schemas: omitted fields stay absent, and descriptions document the runtime defaults. Filling defaults while decoding each managed file would erase an earlier file's explicit settings when a later file sets only one field. E4 tests partial managed JSONC overrides; D15 and the engine computer consumers apply defaults after resolving policy.
2. **The common merge boundary rejects every non-managed source.** In addition to the required project filter, the shared loader drops `computer` unless its source is in `ConfigManaged.read().files`. OS policy records retain the block through their existing separate merge. This also covers custom config directories and downloaded remote org config. Tests use managed-reader fixture records for macOS and Windows; actual OS policy discovery and app identity verification remain with the existing managed-source tests and D15.
3. **The existing admin guide and macOS sample-equivalence test also change.** Both company samples include `computer`; the guide and profile explicitly require Vector 1.99.112 or later. The existing macOS profile test includes the new block in its expected payload. Screenshot dimensions use positive integers; the contract does not specify a policy upper bound for those two fields.
