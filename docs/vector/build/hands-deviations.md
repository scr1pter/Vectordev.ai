# Vector Hands build: deviations from the contract

## 2026-10-28 E0 (shared schema files)

Smallest changes that keep the contract's intent; later packages should build on these shapes.

1. **`ComputerState` is an Effect Schema** (value and type of the same name), not a plain type. It crosses the bridge in `act` and `heartbeat` responses and becomes the `computer.state` bus event (E6b), so it needs decoding. The other desktop views (`ComputerPrefs`, `ComputerPolicy`, `ResolvedComputerSettings`, `ComputerPlatform`, `PermissionsView`, `AlwaysAllowed`) stay plain types; `PREFS_KEYS`, `POLICY_KEYS`, `SETTINGS_KEYS` and `PLATFORM_KEYS` give their keys at run time (compile-checked as complete) for the INV-T1 shape test.
2. **`ComputerApps.category(app, signals)`**: `signals` gains optional `windowClass`, because 2.3 keys the table by window class (ConsoleWindowClass, CASCADIA_HOSTING_WINDOW_CLASS, taskbar classes) but its signature only had `childShell`.
3. **`AppMatcher`** is one app (or family) per entry: `{key: "builtin:<slug>", name, category, macos?: bundleIds[], windows?: {aumid?, windowClass?, binary?}}`, ids case-insensitive, a trailing `*` matches by prefix. `TABLE` exports every entry (never categories first). `ComputerPrefs.unblocked` stores a DEFAULT_BLOCKED entry's `key`.
4. **`builtinRule`** also returns `key` and `name` (for Settings rows and the unblocked check). Added `builtinVerdict(app, {unblocked}, signals)` (the built-in layer of section 2.6 that D15's `access()` should call first), plus `matches`, `find`, `benign`, `isNever`. A DEFAULT_BLOCKED match reports `reason: "user"` (BlockReason has no `default`; the verdict uses `blocked: default`).
5. **System rule vs DEFAULT_BLOCKED.** Disk Utility, Find My and Migration Assistant are Apple platform binaries, so "system and not benign is security" would make them never and contradict 2.3/1.5 K ("removable", [Allow]). `category` therefore treats a system identity that matches DEFAULT_BLOCKED as its listed category. **Cross-package risk (C1, M6, W7):** the helpers' system deny must exempt the DEFAULT_BLOCKED system entries, or a user's [Allow] for them is refused with `protected` at the helper.
6. **BENIGN_SYSTEM** adds ordinary Apple apps under M6's "and similar": Reminders, Contacts, Messages, Maps, Music, TV, Podcasts, Books, Freeform, Stickies, QuickTime Player, Font Book, Dictionary, Weather, Clock, Chess, News, Stocks. FaceTime, Photo Booth, Voice Memos, Home and Journal are left out (calls, camera, microphone, home devices, private journal), so they stay `security`.
7. **Keychain Access** is `password-manager` (reason `passwords`, copy "can't use password managers or Keychain") rather than `security`; 2.3 names it under both and both are never.
8. **Bridge shapes left open by 2.8:** `acquire` returns `{lease}`, `{code: "busy", holder}` or `{code: "permissions", missing}` as 200 bodies; empty responses are `{ok: true}`; `AppQuery` is `{key}` or `{name}`; `openApp.app` also takes `{path}`; `act` takes 1 to 10 steps.
9. **Helper shapes left open by 2.10:** array results are wrapped (`displays.list` gives `{displays}`, `apps.list` gives `{apps}`) so a response stays `{id, ok: true, ...result}`; `cancel`'s argument is `target` because the frame envelope already uses `id`; request ids are non-negative integers; keyboard ops (`input.key`, `input.type`, `input.hold`) carry the `pid` the focused app must belong to instead of `captureId, x, y`; `input.hold` holds a key combo for `ms`; `permissions.request` and `permissions.reset` return the permission status; `app.activate`, `app.launch` and `window.focus` return `{foreground?}`. `HelperEvent` includes `exit`, which only desktop main's supervisor raises.
10. **`ComputerBackend.capture`** returns `bytes: Uint8Array` (the schema package is browser-safe; a Node Buffer satisfies it).
11. **`appKey`** escapes `%` and `|` inside Windows exe parts (`%25`, `%7c`) so two identities can never share a key; ordinary values are unchanged. An exe identity with `verified: false` keys as `unsigned` even if a publisher string is present. `parseAppKey` rejects keys that are not lowercase.
12. **Shared constants live in E0's modules:** `Computer.MENTION_KEY` (D1's `Hands.MARKER` should reuse it), `ComputerApps.VECTOR_APP_IDS`, `HELPER_SUFFIX` and `ELECTRON_HELPER_SUFFIXES` (D1's `helperBundleId` and C1's generator should reuse them), `Computer.LIMITS` (section 2.12 numbers), `Computer.BRIDGE`, `Computer.HELPER_CLI`.
13. **Display text** in ask metadata, part metadata, the mention marker and state rejects control and bidi characters; producers clean text with `Computer.clean(text, max)`.
14. **Not identifiable from identity alone (helpers must cover them):** the Windows Run dialog is matched by its window AUMID `Microsoft.Windows.Shell.RunDialog`, which only the helper can read (W7); Windows Credential Manager shown inside a Control Panel (explorer) window has no identity of its own (W7).
15. Tests live in `packages/core/test` as the contract says, although `packages/schema/test` exists and runs with bun.

## 2026-10-28 D1 (brand constant and naming guard)

1. **`hands.ts` has no imports.** `Hands.MARKER` and the helper bundle id suffix are written as literals instead of importing `Computer.MENTION_KEY` and `ComputerApps.HELPER_SUFFIX` (E0 note 12), so renderer, preload, overlay pages and main copy can read the brand file without loading the Effect schemas. `packages/core/test/hands-brand.test.ts` pins `Hands.MARKER === Computer.MENTION_KEY`, `helperBundleId(id) === \`${id}.${ComputerApps.HELPER_SUFFIX}\`` for every `VECTOR_APP_IDS` entry, and that the helper id is classified `vector` (never-listed).
2. **Extra exports:** `Hands.Channel` (`"prod" | "beta" | "dev"`, desktop main's channel names) and `Hands.CHANNELS`. `helperName` treats an unknown channel as dev, as desktop main's `CHANNEL` does. `Hands` is also in the schema root barrel, next to E0's `Computer` and `ComputerApps`.
3. **The guard is a superset of the contract:** it also reads `packages/ui/src` (a renderer surface package in 4.1, where D2 adds `ui.tool.computer.*`). It matches `Hands.NAME` case-sensitively with any whitespace, `&nbsp;`/`&#160;` or a written ` ` between the words, in code and comments alike ("Vector hands it to..." as a verb is not matched). Exempt: `packages/schema/src/hands.ts`, any file under an `i18n/` directory, `*.test.*`/`*.spec.*` files and files under `test/`, `tests/`, `__tests__/` or `e2e/`. Later packages (D2's `main-copy.ts`, D11's catalog blurb, D13 to D23's desktop main comments) must build the name from `Hands.NAME`, never write it.
4. `hands.ts` writes the name only in `NAME` (comments refer to NAME), and the guard test checks it appears there exactly once.

## 2026-10-28 E1 (permission policy)

1. **`canAlwaysApprove` for `computer_app` accepts only concrete app keys.** The contract's check is `always.every((p) => p.startsWith("app:"))`. The code also rejects the bare prefix `app:` and any pattern containing a wildcard character (`*` or `?`, the two `Wildcard.match` treats specially), so `app:*` or `app:macos:*` can never be saved as Always allow. This is stricter in the safe direction and keeps the contract's own cases (`["app:macos:com.apple.calculator"]` true, `["*"]` false). An app whose key really contains `*` or `?` simply gets no Always offer.
2. **Reason string values.** The contract names `AFTER_SCREEN_REASON` and `FLAGGED_SCREEN_REASON` without values. `AFTER_SCREEN_REASON` takes the engine design's value for the `new_destination` ask ("Text on your screen can steer the agent, and this address or recipient is new: you did not give it."); `FLAGGED_SCREEN_REASON` is the section 1.5 C reason line for flagged screen text. Neither names the feature, so `hands.ts` stays the only place the name is written.
3. **Gap until E2 (no ask is skipped, but INV-C5's "never kept" half belongs to E2).** Because `canAlwaysApprove` is now true for `computer_app` with app keys, an "always" reply is no longer downgraded to "once": the engine's `Permission.reply` pushes the pattern into its in-memory `approved` list, and `PermissionV2.reply` writes it to the saved table, where `savedRules` purges it on the next read (`isSensitiveAction` is true for every `computer_*`). Neither path can answer a computer ask, because `requiresApproval` is now true for every `computer_*` (the engine starts with `needsAsk = true`; V2 returns `ask` whatever the allow rules and saved approvals say, and both auto-resolve loops skip such requests). E2 removes the engine push ("skip approved.push for computer_*") and owns "V2 never saves computer_*"; the V2 save path (`reply === "always" && save.length` → `saved.add`) should also skip `computer_*` there rather than relying on the purge.

## 2026-10-28 E2 (ctx.ask returns the answer; the engine never persists a computer grant)

1. **New read accessor `Permission.Service.approved()`** (packages/engine/src/permission/index.ts), plus the exported type `Permission.Answer = "once" | "always"`. A `computer_*` entry in the in-memory approved list has no observable effect through `ask`/`reply`/`list`, because every `computer_*` request always asks and both auto-resolve loops skip it. So the INV-C5 test "an always reply to computer_app leaves approved empty" needs to read the list directly. Nothing outside the layer implements the interface, so no stubs change.
2. **A computer "always" answers only its own ask.** The contract says to skip `approved.push` for `computer_*`. `reply()` now returns right after resolving a `computer_*` request, so it also skips the same-session auto-resolve loop: an unrelated request that waited in that session stays the person's to answer. Non-computer "always" replies still push and run the loop, which resolves with "always". V2 does the same: `save = reply === "always" && save.length && !isSensitiveAction(action)`. It saves only when `save` is true, and it runs the follow-up loop only after a save. For every non-computer action this matches the old condition, because `canAlwaysApprove` true implies `canAutoApprove` true. Tests: "reply - an always reply to a computer permission answers only that ask" (engine) and the waiting-request block in "V2 never saves computer_*" (core).
3. **`isSensitiveAction` (core V2) already matched every `computer_*` id**, because `canAutoApprove` is false for the whole prefix. It was not extended; a comment now says so. The V2 save path now skips sensitive actions instead of relying on the purge in `savedRules`, as E1's note asked.
4. **The plugin bridge stays `Promise<void>`.** `packages/engine/src/tool/registry.ts` maps `toolCtx.ask(req)` through `Effect.asVoid` before handing it to a plugin, because `@vectordevai/plugin`'s `ToolContext.ask` returns `Promise<void>` and the wider type does not fit it. The plugin API is unchanged.
5. **Test harness.** "V2 never saves computer_*" uses an in-memory `PermissionSaved` replacement that records every `add`. Without it the test could not tell a write that the next `savedRules` read purges from no write at all: under the old code the post-save loop purges it within the same `reply`.

## 2026-10-28 E3 (agent defaults and plan-mode gating)

1. **Tool-list asks cover both kinds of tool-list agent.** The contract points at the research agents' block (374-376). The read-only specialists (explore, review, judge, security) also build their rulesets from a tool list, so both now spread `computerAsks(tools)`, a small function exported from `packages/engine/src/agent/agent.ts`. It returns the four `computer_*: "ask"` entries when the list includes `computer`, and nothing otherwise. No agent's list includes `computer` today (subagents never get the tool, INV-S10), so the function is exported for the test to check directly. Those agents keep denying every `computer_*` through their `"*": "deny"`.
2. **Plan mode's denies are applied last as well.** The contract adds `computer_interact: "deny"` and `computer_sensitive: "deny"` to the plan block, which merges before the user's rules. In this codebase user rules override plan mode's own rules (for example `task: {general: allow}`), so a user or trusted-repo `"*": "allow"`, or `agent.plan.permission.computer_interact: "allow"`, would have reopened them. The two denies stay in the plan block and are also applied after the config loop and the user ceiling, so no rule reopens them. `computer_app` still asks in plan mode. The `computer` tool itself stays offered, because `Permission.disabled` keys on the tool id and not on `computer_*`. E6 can therefore read plan mode's observe-only state from the ruleset (`Permission.evaluate("computer_interact", "*", ruleset).action === "deny"`) as well as from the agent name.
3. **No allow evaluates to allow for a `computer_*` permission (stricter, ruleset level).** After the config loop, a final pass puts an ask for the same pattern right after every allow rule that covers a computer permission. That covers `"*": "allow"`, `"computer*": "allow"` and named or pattern-specific allows, from user, repository and agent config. So the merged ruleset reads `ask` where the runtime asks anyway (`PermissionPolicy.requiresApproval`, E1), and a deny written after the allow still wins. A deny written before an allow now reads as `ask`; before this pass it read as `allow`. The tool id `computer` is not touched. Session-level rules, which are merged after agent rules at run time, are outside this pass. requiresApproval still makes them ask, and E6's refusal in plan mode is the authoritative check there.

## 2026-10-28 E4 (company-only computer config)

1. **Optional fields preserve managed-layer precedence.** `ConfigComputerV1.Info` follows the existing config schemas: omitted fields stay absent, and descriptions document the runtime defaults. Filling defaults while decoding each managed file would erase an earlier file's explicit settings when a later file sets only one field. E4 tests partial managed JSONC overrides; D15 and the engine computer consumers apply defaults after resolving policy.
2. **The common merge boundary rejects every non-managed source.** In addition to the required project filter, the shared loader drops `computer` unless its source is in `ConfigManaged.read().files`. OS policy records retain the block through their existing separate merge. This also covers custom config directories and downloaded remote org config. Tests use managed-reader fixture records for macOS and Windows; actual OS policy discovery and app identity verification remain with the existing managed-source tests and D15.
3. **The existing admin guide and macOS sample-equivalence test also change.** Both company samples include `computer`; the guide and profile explicitly require Vector 1.99.112 or later. The existing macOS profile test includes the new block in its expected payload. Screenshot dimensions use positive integers; the contract does not specify a policy upper bound for those two fields.

## 2026-10-28 E5 (availability and registration)

1. **Registration precedes execution in the build order.** E5 adds a fail-closed `ComputerTool` scaffold so the registry and capability-derived input schema are testable now. Every execution returns `unavailable` without making a command request. E6 replaces that executor after E6a, E7 and E8 supply its transport, classifiers and screen handling.
2. **Availability is an Effect service.** `ComputerAvailability.Service` shares one validated bridge capabilities probe per instance for 30 seconds; `unavailable()`, `capabilities()` and `actions()` reuse it. Company policy and Vector Local's current egress policy are checked without waiting for the bridge cache to expire, so a new restriction applies immediately. The public capability has optional `protocol`, because the required no-bridge response has no negotiated version. A bridge `permissions` reason with supported actions remains available to the tool and client for onboarding; all other failure reasons and an empty action list are unavailable.
3. **Reader models remain eligible.** The E5 introductory vision-only wording conflicts with the explicit reader mode in Sections 1.4 and E6b. E5 does not require image input. Free-model entries must explicitly say `no-training`; an absent data policy on a free-model entry is withheld. Ordinary models without a free-model entry remain eligible.
4. **Wire reasons and model reasons have different vocabularies.** The client receives the bridge's detailed reason where available; failed validation or transport is `bridge_unavailable`, and the reserved remote backend is `remote_unavailable`. The model uses E5's fixed reason union and Section 1.4 copy; helper/transport failures map to `desktop`. Both surfaces agree on whether the tool is available.
5. **The conversation tool switch needs its own explanation.** The contract tests `tools.computer: false` but gives it no reason code or copy. E5 adds `disabled` and “Vector Hands is turned off for this conversation.” (built from `Hands.NAME` in runtime code). It withholds both the tool and the client capability; a valid mention whose tool was removed by the conversation's rules uses the same explanation.
6. **A recovered bridge refreshes the offered decoder and schema.** Registry state initializes built-ins once. If that first capability request failed, retaining its empty action schema would leave the tool unusable after the 30-second probe cache recovered. E5 refreshes the computer definition when it is offered, using the cached current action list. E9 owns the separate byte-stable provider conversation seam.

## 2026-10-28 E6a (bridge transport deadlines and cancellation)

1. **A dedicated Node HTTP client owns no hidden deadline.** The service uses Effect's `node:http` client with a scoped agent and `timeout: 0`; the shared fetch client can impose a header deadline before a long act or handoff finishes. The transport owns the complete act deadline, including response decoding, and a ten-minute queued-acquire deadline. `awaitControl` and `handoff` have no overall deadline. Other commands have a 30-second deadline; cancellation cleanup has its own five-second bound and never recursively cancels itself.
2. **Long polling preserves the root queue.** Desktop D13/D19 must return `pending`/`busy` at least once every 60 seconds. The engine repeats those replies, with a 100 ms pause to bound retries from an immediately busy bridge. It does not force a disconnect every 60 seconds: the contract makes disconnect a cancellation, which would otherwise discard that root's queue position on every poll. Act responses with `waiting` return immediately; E6b decides when to call `awaitControl`.
3. **A queued root needs cancellation without a lease.** The original `cancel` request required a lease, but `acquire wait:true` has none. Disconnect is insufficient when abort arrives between poll replies, leaving no active request to disconnect. `cancel.lease` is therefore optional: **without a lease, D13/D19 must remove only the authenticated request's `rootSessionID` from the acquire queue and must never stop or release an active holder**. A supplied lease retains the existing holder-work cancellation semantics. The transport sends this root-only cancellation on queued timeout, abort, or fiber interruption, including between polls. The shared schema and fake bridge pin this distinction for the desktop implementation.
4. **Transport tests are split by boundary.** `test/computer/transport.test.ts` uses an injected Effect HTTP client and TestClock for long deadlines and interruption; `test/tool/computer.test.ts` exercises the real local HTTP transport against the fake bridge. Neither accesses OS permissions, input, or screen content.

## 2026-10-28 E7 (shared step checks and screen provenance)

1. **Pure classifiers receive observed context.** `ComputerSensitive.Context` carries canonical/protected paths, the result of the caller's `SessionMemory.source` check, menu shortcuts, clipboard text, resolved program paths and destination evidence. The classifier performs no filesystem or OS reads. E6 and D16 must supply these from their own observations, including canonical paths for aliases and configured instruction files. App launching is a bridge command rather than a `Computer.Step`, so the classifier also accepts `{kind: "open", path}` for that boundary; a launch requires its full resolved path.
2. **Key layout and menu inputs are explicit data.** `ComputerKeys.Layout` supplies the platform and physical-key character levels. Missing physical mappings or modifier levels refuse. `MenuShortcut` includes the observed label as well as the combo, so a custom macro/script binding cannot pass as an ordinary editing shortcut. `resolve()` shares the interpretation with sensitive-action checks. Native helpers must still resolve the actual current layout and focused app immediately before input.
3. **IDE input follows the existing shared category contract.** `ComputerApps.CLICK_ONLY` already allows clicks and keys while forbidding typing. E7 preserves navigation and copying, refuses text insertion/edit keys and observed editing menu actions, and asks before Run/Build/Debug actions, including their observed menu shortcuts. Source changes remain with Vector's edit tools.
4. **Destination extraction is conservative candidate detection.** `ComputerEntities.unvouched` runs only after `SessionMemory.taint` is set and compares only user-role `SessionMemory.said()` text. It preserves complete URL paths, queries and fragments, and excludes synthetic, ignored, tool, assistant and attached-file content as evidence. Enclosing destinations win over embedded emails/numbers; ambiguous long formatted number runs and unlisted IBAN formats remain candidates for review rather than disappearing. Credential checks run before destination asks.
5. **The screen fence follows the existing source-first API.** `fenceScreen(source, text)` mirrors `fenceWebPage(source, text)`; the contract omitted the text argument. `flagged` was already exported. App/window labels are cleaned, quoted, capped at 40 characters and kept inside the nonce-bound screen fence; a fixed note flags instruction-like labels without repeating their content outside it. Existing web-fence output stays compatible.

## 2026-10-28 E8 (capture sizing, history, and repeat detection)

1. **Native eligibility uses a conservative explicit list.** The contract refers to native OpenAI IDs and Claude “listed siblings” without providing a complete table. E8 recognizes actual API IDs `gpt-5.4` and `gpt-5.5`, and Opus/Sonnet/Haiku 5.5, only with their matching direct provider and SDK package. Catalog aliases or a newer version number do not imply wire support. E9 still owns the runtime, authentication, and configuration gate; other vision models retain the generic tool.
2. **Capture plans respect both attachment and company limits.** The contract supplies no numeric provider pixel-cap table. Anthropic receives a conservative 1,150,000-pixel ceiling in addition to the dimension bounds; other families use the bounded width times height. Physical pixels are fitted once, independent of display DIP scale. Tiny budgets and extreme aspect ratios remain within all three bounds.
3. **Dimensions alone cannot guarantee unchanged image bytes.** `Image.normalize` also enforces `max_base64_bytes` and may re-encode or resize an otherwise dimension-compliant image. The normal processor path rejects a computer result when normalization fails or changes its URL/MIME, rather than retaining coordinates for different pixels. E6 must validate captures before returning, invalidate rejected frame state, and enforce the same guarantee for direct completion on abort. Its interaction metadata must retain the perceptual hash even when image output is disabled.
4. **Both repeat guards compare completed evidence.** Computer calls bypass the old input-only preflight check. After a normal result is settled, the legacy guard reads consecutive tool results across assistant messages in the same user turn. It and SpendGuard use canonical action/target fields and the perceptual frame hash, excluding intent, capture IDs, counters, and encoded images. Observations and results without a verifiable hash receive a per-call digest. Aborted completion never opens a new permission ask.
5. **Compaction uses a preflight visual estimate.** No reusable image-token estimator existed. The implementation removes image transport payloads from text estimation and adds provider-family visual estimates using bounded image headers or saved frame dimensions. Exact usage is only known after a provider request. Unknown dimensions use a conservative 2000×2000 fallback; Gemini and generic heuristics cap at 8192 visual tokens. No media fetch, pixel decoding, or provider call occurs. Tests cover multi-MiB payloads, malformed and extreme headers, and retained-tail selection.
6. **Pruning changes model requests only.** Stored transcript attachments remain intact; only selected completed computer parts lose media and gain the removal marker. E9 owns native server-side clearing and OpenAI placeholder images, alongside its stable tool-definition seam.

## 2026-10-28 E6 (root leases, app consent, and single actions)

1. **The conflict-resolution table governs app consent.** Section 1.3 explicitly says one `computer_app` ask covers seeing and operating an app; E6 bullet 3 would otherwise ask at observe level for a first read and again for a click. Normal tasks request interaction consent at first app touch, including reads. Plan mode and an app-specific interaction deny use observe consent and cannot send input. The legacy observe/interact permission names remain policy checks, never additional prompts.
2. **The caller chooses an approval ID.** `Tool.Context.ask` now accepts an optional `id`; the existing SessionTools wrapper already forwards it to Permission. The engine passes that exact ID to `grant` and `remember`. A rule-only context returning no answer cannot grant access. Desktop D16 remains the authority: it must observe the matching ask and user reply before accepting either command.
3. **Program paths resolve before launching.** The original `access` accepted only a name/key, while `openApp` accepted paths without an approval field. `access.app` now also accepts a path, which D16 must resolve without launching. `openApp.requestID` carries the separate once-only run-program approval for the canonical resolved path. The agent's path and an accessibility label are not identity evidence.
4. **Sensitive approval binds the whole proposed step.** Labels, app keys and frame IDs alone cannot distinguish same-labeled targets or different key combinations. `SensitiveAskMetadata.stepDigest` is the SHA-256 of canonical step JSON, computed by shared `ComputerSensitive.digest`. D16 must match it against the exact bridge step (or canonical open path), alongside app/frame evidence, before consuming a sensitive request ID once. The model never supplies this proof.
5. **Inspection can carry observed classifier context.** Optional `layout`, `focusedMenuShortcuts`, `programPath`, and `clipboard.text` fields supply E7's pure checks. They come from the desktop, never model assertions. Layout must match the app's platform; program paths must be canonical. Clipboard text means the complete contents within the bound, never a truncated preview. Missing or oversized clipboard evidence does not waive the desktop's live credential/paste checks. D16 and the native helpers must supply and re-check their actual observations before input.
6. **A later mention means a later message.** The root conversation retains denial message IDs across task boundaries. An app marker in the same message that received Deny cannot reopen that ask; a later marker lifts only the denial and asks again. Cached task grants never replace a fresh desktop access verdict, so revocation and changed identity take effect.
7. **One authoritative idle event ends the lease.** The existing SessionStatus service publishes `session.status` with idle followed by deprecated `session.idle`. Consuming both can stop a successor task started between them. The global ComputerSession service consumes the status event, cancels the task generation, drains its FIFO, and releases the lease. Conversation denials survive; frames and task grants do not. D13 must also release an acquire whose connection disappears before the engine receives its lease; root-only cancellation still removes only a queued root, as specified in E6a.
8. **Successful input gets a fresh budgeted capture.** The existing `act` request has no capture budget and its response lacks visible apps, hidden count and pointer. E6 follows it with `screenshot` using the active model's bounded plan, rather than trusting uncapped act pixels. It keeps the perceptual hash even when image output is disabled. This costs an extra capture; D19 may optimize only while preserving those guarantees. Image verification happens before a frame is remembered or returned, including the direct-completion abort path; rejected captures invalidate coordinate state. The processor also invalidates that state if its later normalization rejects the image after settings changed. Zoom never replaces the full-frame ring.
9. **Public API generators are unaffected.** These bridge request/inspection and ask-metadata additions are internal desktop-engine contracts; they do not change Server HttpApi, Protocol manifests, configuration inputs, or the SDK's public surface. Schema, core and engine typechecks cover the affected packages.
10. **Screen text stays inside an intact fence.** The ordinary tool wrapper can truncate after fencing and spill full output to a generic tool-output file. The computer tool bounds and cleans text before fencing, then supplies its own `truncated` metadata so the wrapper does neither. The notice remains inside the fence; no output path is created. It honors configured limits up to a fixed 50 KiB/2000-line ceiling while reserving space for the fence and fixed explanatory text.
11. **FIFO and interruption have explicit ownership.** Deferred tickets preserve root call order even before an awakened waiter runs. Each call has a tracked interruptible worker; task-wide AbortSignal subscriptions persist between calls. The service interrupts and joins workers before releasing a lease, including when the caller is directly interrupted. This avoids waiting for the caller's own race cleanup while holding its cleanup latch. Tests cover both active calls and abort during model thinking between calls.
12. **Current permission denials override desktop grants.** The tool evaluates the agent and persisted session rules even without a caller denial callback, and also honors callback denials. Global observation/app denials stop before acquiring a lease; app-specific denials stop access or withhold captured pixels and invalidate coordinates. The latest full frame retains all visible identities, including Always-approved apps absent from the local grant cache, so a later zoom rechecks their policies. Interaction denial limits reading to observation approval. Fake-bridge regressions cover policy changes after earlier approval and configured instruction-file globs.

## E6b — Batches and attended control flow

1. **The state event belongs to the compatibility stream.** `ComputerEvent.State` is the single canonical `computer.state` definition and joins `EventManifest.Definitions`, reaching `/global/event` and the legacy SDK. It stays out of `ServerDefinitions` and the current Protocol event union because this release explicitly excludes V2 sessions from computer use. The current client generator is still run as requested; it should have no surface change. This follows the schema package's event-classification rule rather than promoting a V1-only event into the current API.
2. **Questions gain typed metadata.** Existing V1 Question requests had no metadata field. An optional union of `HandoffQuestionMetadata` and `CheckInQuestionMetadata` is now accepted by the Question service and retained in the request/event. Ordinary questions omit the field. The current Question contract is unchanged.
3. **A pause can wait by lease.** `awaitControl.waitId` is now optional: pointer waits retain their exact returned ticket, while an ordinary pause waits on the authenticated lease's control state. The original act pause/state and typed error did not supply a ticket. D19 must distinguish these two cases and never resolve a different lease's wait.
4. **Live batches retain engine policy restrictions.** `act.allowedApps` names only identities checked against the active agent/session policy for this call. It restricts access and never grants it. D16 must return an app pending gate for a live target outside this list, even when a desktop grant already exists; absent or empty lists authorize no engine-checked target. Without this field, a later batch step could reach an app whose desktop grant predates an engine policy denial. The engine adds an identity only after resolving and checking it at a pending gate. A fresh access verdict may confirm sufficient existing task or Always consent without another ask; only a newly observed ask ID is forwarded, never an old approval replayed merely to satisfy the policy gate.
5. **One step can need two proofs.** The existing approvals array can now hold up to twice the batch-step limit: distinct app and sensitive request IDs may share a rebased index. A new destination is checked before input, then asked again against a changed pending target when necessary. D16 must treat every supplied sensitive proof as a required gate for its observed ask reason, match the complete step digest and live target, and consume it once. A stale target proof must produce another pending gate even when the desktop's own classifier would otherwise permit the step; it must never be silently ignored. The ask's original step index describes the user's batch; the bridge approval index describes the resubmitted suffix.
6. **Generic batches can contain non-input actions.** The generic schema includes reads, captures, open and focus, while the wire `Step` union contains input and wait only. Contiguous input steps are sent together through `act`; standalone generic actions run between those groups in order. Executed prefixes are never replayed. After a pause or handoff, a fresh observation returns to the model and the remaining old actions are not resumed automatically.
7. **The lease owns its heartbeat and clock.** A two-second heartbeat continues between tool calls and stops with its task generation. Active time uses Effect's clock and excludes nested asks and desktop waits. Any heartbeat failure stops and releases the known lease; the desktop's engine-quiet timeout remains a separate backup. State is validated against the lease and holder before publication and throttled across heartbeat and act reports to once per second.
8. **Current-call observations count as outside content.** A batch can inspect a target before any of its output reaches saved history. `ComputerEntities.unvouched` therefore accepts an explicit observed flag from the tool's real inspection; its default behavior for other callers is unchanged. This closes the gap for new destinations proposed during the same call while retaining exact user-supplied destinations as evidence.
9. **Completed steps remain counted if capture fails.** Input counts come from validated `act.done`; reads and other standalone actions count once. Open/focus are counted as soon as their command succeeds, before capture. A separate completion marker distinguishes failure of an action from failure of its follow-up observation so the exact failure sentence is emitted for every unexecuted suffix action. Configured text budgets are shared across batch outputs before fencing, with no generic output-file spill.

## E14 — Private local action record

1. **The record has a strict projection.** The Effect service writes only its bounded, typed fields under `Global.Service.data/computer/log`, using Node-compatible filesystem services. Typed input becomes its length and a 12-character SHA-256 prefix. Unknown fields, screenshots, full tool inputs, intent and reasons are never serialized. Labels and correlation fields cannot echo the supplied typed text; unsafe call IDs become hashes. Log errors contain a fixed message without the original input or filesystem cause.
2. **Audit failure stops further input.** Attempt and approval records are written before the associated input or grant. Outcomes are recorded only for confirmed executed steps; a later file failure cannot turn completed input into an unexecuted step or cause it to be replayed. Stop and lease cleanup remain available even when the record cannot be written. Approval records use the original batch action index, independently of a standalone app launch's protocol step index.
3. **Deletion is prepared before the durable event.** The existing event bus isolates listener failures after committing deletion, so a listener alone could leave an orphaned file. Session removal now retires the computer root, drains its work, and removes its record before publishing the deletion event. Retirement and log tombstones reject concurrent new calls and late writes. A native mutation already in progress retains the per-root mutex until it settles, even when its caller is interrupted; known desktop input is released before joining such workers. The deletion listener also covers replay and other event paths; Session's dependency initializes it when deleting an older session before any tool use in this process. IDs that could never form a valid log filename are ignored by removal without constructing a path.
4. **Background control decisions use a reserved call label.** Heartbeats can observe a take-over or Stop while the model is between tool calls. These records use `call: "control"` and record actual control transitions separately from the one-second UI event throttle. The lease and holder are checked first; repeated identical heartbeat states do not create duplicate transition entries.
5. **Existing export roots exclude the record.** Ordinary server logs live at `Global.data/log`; the action record is in the separate `computer/log` directory. Desktop debug export collects only its own `userData/logs` and explicit server `vector/log` roots (`packages/desktop/src/main/logging.ts`). Crash uploads are disabled there, and renderer error reporting has no local-file attachment path. No broader export path or new upload is introduced.
6. **No public generator input changes.** The log service and deletion coordination are internal engine behavior. Public protocol, SDK, configuration and HTTP schemas are unchanged by this work package.

## E9 — Native provider adapters and generic fallback

1. **The shared configuration remains `auto | off`, default `off`.** E9's mention of `on` conflicts with Section 2 and the existing configuration schema. `auto` allows a native choice on a validated user mention; simply offering the tool does not opt a conversation in. A conversation that first uses the generic tool stays generic. Stored computer-call metadata reconstructs the choice after a restart; unsupported models, credentials or a later off switch return to the generic path. Anthropic subscription sign-in and OpenAI sign-in without the required fetch override retain the generic tool. Model quality tiers do not promise native transport.
2. **The existing native metadata field stays compatible.** `ToolDefinition.native` already accepted an arbitrary record. Its schema now also accepts the literal `computer`; existing record values retain their meaning. Only the selected conversation's computer definition receives that literal. The obsolete OpenAI hosted mapping is removed because these calls execute through the ordinary local tool and its consent checks.
3. **Pixel scrolling has an explicit wire unit.** OpenAI scroll deltas are pixels, while the generic tool's amount is a bounded wheel amount. Bridge `Step.scroll` and helper `input.scroll` gain optional `unit: "pixel"`; omission preserves generic behavior. A trusted native context carries bounded exact deltas and their batch indices separately from model-facing arguments. Coordinates still use the full-frame validation. D19, M5 and W4 must preserve and honor the unit rather than treating pixel deltas as wheel counts.
4. **Provider checks use the existing desktop proof boundary.** Up to three distinct provider flags receive separate once-only sensitive asks bound to the first proposed input step and its observed target. Local sensitive checks still apply. A changed pending target requires new matching proofs. Acknowledgements are emitted only after validated execution of that step. Malformed or excessive checks refuse before acquisition. Flagged calls containing standalone reads, open or focus refuse because those commands have no matching input-step proof slot; ordinary native reads remain available. These limits keep every flag visible without truncating permission evidence or expanding the approval wire.
5. **Unknown outcomes remain unknown on replay.** A known unexecuted decline removes the OpenAI call and its paired reasoning and supplies a status note. A partially executed or interrupted call retains its provider call and a screenshot or placeholder; it is never described as wholly unexecuted. Result metadata is projected separately from call metadata so a saved request cannot manufacture an acknowledgement. Anthropic results infer their toolset from the matching call even when a synthesized error has no metadata.
6. **Anthropic clearing preserves signed history.** The generic path freezes the computer description and schema while retaining the current executor, including when the experimental LLM runtime transports the generic tool. After a process restart or tool-availability change, unverifiable old signed thinking blocks are dropped; new blocks under the stable definition are retained. Title and memory helper requests sharing the session do not change that state. Computer screenshots stay in history and are cleared server-side using `clear_tool_uses_20250919`, excluding other tools and keeping inputs. The native Anthropic adapter supports the same clearing settings and merges the required beta header with caller headers.
7. **Provider shapes are contract fixtures, not live recordings.** The new tests replay explicit local wire fixtures and fake transports. They do not claim a successful live request to these provider versions. Native transport remains opt-in; `native_tools: "off"` is the supported generic fallback if a provider shape differs. Key aliases normalize by desktop platform before the shared live layout and sensitive checks.
8. **The wire additions are internal.** Scroll units, provider adapters and execution context do not change public HTTP, Protocol, configuration or SDK generator inputs. Shared schema, core, LLM and engine typechecks cover the touched packages.

## E10 — Shell confirmation after computer use

1. **The approval marker preserves command policy matching.** Shell requests retain their ordinary per-command patterns and add the reserved `#after-screen ` marker when fresh confirmation is required. Both permission evaluators remove that marker before matching configured rules, so an explicit command denial still applies. The comment prefix avoids confusing the marker with an ordinary executable named `after-screen`; the existing unread-command restriction still applies after normalization.
2. **Each command needs a fresh once answer.** After a completed computer part in the current user turn, shell requests have no Always choices. Configured allows, remembered approvals and client auto-accept cannot answer them. The executor requires a once answer and checks again immediately before spawning, after permission, environment and command-preparation waits. A completion during an earlier approval therefore adds a fresh confirmation before the process can start.
3. **Turn state follows the persisted root conversation.** The processor marks computer completion only after saving the completed tool part, including observations and refusal results. The state service can recover the current turn from completed parts in root history. Shell ancestry uses the stored session parent ahead of context hints and follows the parent chain for nested subagents. Lease release does not clear same-turn confirmation; idle, a new user turn and deletion define its boundaries.
4. **A draining lease still gates desktop commands.** The nonblocking held query includes active and closing tasks. If release cannot be confirmed, it remains true through the desktop's engine-silence watchdog window. Known desktop-control commands are refused before approval and checked again before spawn, including when a lease was acquired during a pending shell ask.
5. **The classifier is a maintained pure denylist.** The core utility recognizes known screen-capture and input-synthesis programs, ordinary launcher forms and selected inline desktop APIs from command text or parsed words. It performs no process execution, filesystem inspection or OS input. It does not claim to interpret arbitrary programs or scripts on disk; ordinary build and file commands keep their existing permission path. This repository has no separate terminal tool to patch, so the existing shell executor is the integration point.
6. **No public generator input changes.** The approval marker, classifier and lifecycle queries are internal behavior. Public HTTP, Protocol, configuration and SDK schemas are unchanged by this work package.

## E11 — Community computer-control MCP policy guard

1. **The existing effective configuration supplies managed policy.** The stdio launcher reads `Config.computer` immediately before constructing its transport. 2. **Default app denial also restricts the community server.** Besides `enabled: false` and any macOS or Windows app rules, `default_app_access: "deny"` triggers refusal. That setting denies unspecified apps even when the explicit rule maps are empty; permitting unrestricted community desktop control would bypass it. Allow rules also count as company app rules, regardless of the host OS. Absent policy, empty app rules and unrelated computer settings do not trigger this guard.
3. **The catalog's package runner is covered.** The catalog starts `uvx --python 3.12 computer-control-mcp@0.3.14`, rather than directly executing the server name. A focused pure argv matcher recognizes that launch, executable paths and extensions, versioned distribution names, Python entry points and common environment/package runners. It checks resolved command arguments before process construction, performs no OS operations, and does not inspect arbitrary scripts or shell source.
4. **Refusal uses the existing failed MCP status.** The message points to `Hands.NAME` as the supported path and includes no resolved command, environment value or secret. Initial startup and explicit add/connect paths share the same local launcher. Catalog visibility and community warning copy remain D11's work.
5. **No public generator input changes.** This guard adds internal engine behavior without changing public HTTP, Protocol, configuration or SDK schemas.

## E13 — Screenshot privacy and durable deletion

1. **Screenshot consent belongs to one manual publication.** Local export and share preview default to removing computer media. An explicit `includeScreenshots` request can include bounded PNG, JPEG or WebP data URLs in a public computer tool entry. Automatic creation forces the flag off; live updates strip screenshots at both the engine and public-share API. Remembered sharing consent never remembers the screenshot choice. Ordinary uploaded files and other tools' attachments retain their existing behavior.
2. **Privacy follows every transcript transport.** The shared projection covers V1 attachments, native tool content, known provider-result copies and portable public screenshots. Guest JSON responses and both event streams use it, including framed SSE returned by owner-authenticated workspace proxies. Sync history, replay and workspace moves also project media for owners. Workspace SSE connections send the restrictive `x-vector-workspace-sync` header so the whole remote stream is projected; durable sync-event copies are projected for every viewer. The header grants no access. The local owner's ordinary UI events retain screenshots. No phone/session relay exists in this workspace; the desktop task relay carries summaries and control, not transcript media.
3. **Native events resolve their owning tool.** Progress, success and failure events identify a call without repeating its tool name. Projection resolves that name from the current message, durable call/import history or the same replay batch before removing media. An outbound event whose tool cannot be resolved loses media rather than exposing an unidentified screenshot. Known ordinary tools keep their files. Decoded DateTime values retain their prototypes during projection.
4. **Replay protection lives at the common conversion boundary.** Every legacy conversion rechecks the chosen model's training policy and strips computer images for a may-train or unreviewed free model. The current runner carries the resolved route's policy as internal model metadata and applies the same rule to imported native computer transcripts. Text-only helpers use the same projection; compaction keeps its existing `stripMedia` behavior. The inspected Brain, memory and learned-skill paths consume text or explicit top-level user files, not computer tool attachments, so no new screenshot-reading extractor is added.
5. **Pruning removes all durable local copies.** The owner-only route updates legacy parts, native messages, matching historical events and retained initial share archives. Legacy state records `metadata.screenshotRemoved`; native state uses `structured.screenshotRemoved`. Selection supports a cutoff, a session, or `all: true` alone. Delete-all reserves the database connection through the immediate transaction, `VACUUM` and a checked truncating WAL checkpoint; a busy checkpoint is an error. Existing published remote shares remain governed by their explicit publication and unshare controls.
6. **Deletion survives stale completions and replay.** Event publication checks current and historical tombstones inside its write transaction before encoding, projection and notification. It strips late media while preserving the removal marker, and `Session.updatePart` returns the normalized committed part. Pruning does not republish captured whole parts, which could overwrite a concurrent metadata update; D23 must invalidate and refetch both legacy and native history caches after deletion. Exact retries of known computer events may differ only by the screenshot projection, allowing a remote redacted copy to reconcile with a local full copy; all other transcript fields still match exactly, ordinary tool media remains significant, and replay does not replace the existing row.
7. **A pending share cannot restore a pruned archive.** Initial snapshot capture and storage share an immediate transaction with database writers. After a remote request, share persistence retains only the current stored initial archive, rather than the pre-request copy. This prevents a concurrently completed prune from being undone by a late share response. Live-share comparisons use the screenshot-free baseline, so an unchanged manual opt-in survives flush, shutdown and restart; an actual transcript update removes the public screenshots.
8. **Public generator inputs change in this package.** The screenshot opt-in and preview/export queries extend public sharing contracts, and the new prune endpoint extends the legacy instance HTTP API. The current client and legacy SDK generators cover those surfaces; D7 still owns the checkbox and public-viewer screenshot rendering. D23 owns scheduled pruning, Delete all and history-cache refresh.
9. **Event readiness includes the privacy subscription.** The global event route now registers its listener before emitting `server.connected`, matching the instance event route's readiness guarantee. Raw event streams capture the database resolver before the request context ends, preserving known ordinary-tool files during later pulls. Guest proxy projection preserves SSE IDs and content type and reassembles split JSON chunks before removing media.
