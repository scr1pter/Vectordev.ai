# A12 owner controls

A12 is implemented in the local `codium-next` draft. All validation below has passed and independent financial/security review is closed. The canonical source push and complete CI remain pending. No live provider configuration, payment, deployment or sales enablement was performed.

## Private dashboard and authorization

`/owner/codium` is an unlinked, noindex static shell with a client-only React island. Production pruning retains the page and removes it from the sitemap. Private records are fetched after authentication and never serialized as build or SSR props. The client uses the existing account session, refreshes every 60 seconds, clears private data when identity changes, and never automatically retries a mutation after sign-in. Both the API's effective sales summary and the funding badge reject future-dated or fifteen-minute-old readings.

All six owner endpoints use `requireUsageOwner`: verified Google identity and the existing owner allowlist. Every mutation additionally requires the verified token's original OAuth `amr` timestamp to be nonfuture and less than ten minutes old. A newer JWT `iat`, password event or MFA timestamp cannot satisfy that requirement. The existing account-deletion sign-in helper is unchanged. Mutations validate trusted JSON, use a persistent rate limit and write requested/completed audit entries with a hashed owner identity. Responses, audits and errors omit email addresses and raw provider/account objects.

The shared private wire schema projects funding, bounded history, observed runway/watchdog, plan counts and MRR, thirty-day risk counts/ratio, outbox/dead-letter/store/replay/sweep health, runtime controls and a readable Stripe checklist. Provider or truncated-list failures leave counts and refund quotes unknown. Account discovery is bounded at 200 stored account IDs and labels an incomplete listing. Later service budgets remain explicitly unconfigured. A model removed from a later catalog can still be restored from its persisted kill set; disabling a new unknown model is refused.

Owner replay accepts Unix seconds within the last thirty days and preserves the scheduled replay cursor. Reconciliation and risk clearing use the existing account lease and authoritative provider reads. Risk clearing refuses open or unknown disputes and pending owner-end/deletion work. It acknowledges exact lost-dispute IDs and exact warning IDs; a later open transition or a new warning on the same charge still applies. Clearing a hold does not synthesize payment or uncancel a subscription.

## Refund and end operation

The new endpoint requires the dashboard's charge, remaining refund amount, governing subscription and period-start confirmation fences, including explicit null/zero when nothing is refundable. The server recomputes each value; client amounts are comparisons, never refund instructions. A changed payment returns `CODIUM_REFUND_CHANGED` and the UI requires a new confirmation naming the account, amount, charge and scope: all owned Codium subscriptions and pending checkouts stop.

An immutable operation ID, customer, source charge and subscription/checkout targets are saved atomically with a unique reconcile outbox publication. The frozen snapshot and current provider key disable precede cancellation or refund. Full outstanding allowance remains reserved until termination finishes. Retries retain the same targets and provider idempotency keys. A lost response after a successful refund is recovered by exact operation/attempt metadata and refund ID rather than creating another refund.

Checkout discovery reads every session status and explicitly includes the durably stored checkout, using the real creator's customer, mode, `client_reference_id` and configured billing metadata. A second subscription/payment read fences completion between discovery reads. Completion after that fence remains bound by the immutable captured session and its resulting subscription is canceled. Incomplete discovery refuses the action.

A successful HTTP refund response may still mean pending, action required or failed. The operation persists the exact refund ID, amount, attempt and status, stays frozen for pending/failed refunds, and finishes only after successful refunds cover the full source charge and the refreshed charge agrees. Ordinary retries never start a new attempt after a conclusive failure; only a new explicit owner confirmation does. A partial prior refund returns only the remaining confirmed amount. A completed refunded period retains separate settled-refund provenance through ordinary reconciliation and a fresh zero-refund end operation. That operation can still expire a newly pending checkout. The reason matches only the original subscription and period; a later paid subscription stays independent and an old confirmed retry never retargets it.
