# Multi-agent parity: deviations from the build contract

## 2026-10-26 WP1 (shared contract)

- `sizing.learn` (A.4): its description never carried "only work you ask to be thorough gets subagents"; that phrase was in `sizing.auto`, which now reads as A.4 says. `sizing.learn` was left unchanged.
- `SubagentRecord.workflow` (4.6): the run variant's `progress` is typed `Record<string, unknown>`, because `WorkflowProgress.Progress` (core orchestration, WP29) does not exist yet. `SubagentLifecycle.read` checks it is an object. WP29 narrows the type and the check.
- Defaults for narrowing (4.2 "min(repository, user ?? default)"): added `ConfigV1.SubagentDefaults` (running 8, per_request 32, usd 25) and `ConfigV1.WorkflowDefaults` (max_agents 100, concurrency 16, steps 40 per agent, per_agent_steps 60, minutes 120, runs 1) in `packages/core/src/v1/config/config.ts`. WP5's `TaskLimits.DEFAULTS` and WP29/WP30's workflow constants should read these, so the narrowing and the runtime never disagree. A workflow key with no default (usd, tokens) keeps the repository's value when the user has none, which only narrows "no ceiling".
- `sizing.subagents` description: the contract's text says a repository "may only turn forks off and narrow models"; the 4.2 table also lets it shorten the user's `ask_timeout`, so the description says so.
- Narrowed `sizing.subagents.models` with no model in common with the user's list is kept as `[]` (no extra model allowed), the narrowest value, rather than dropped.
- `SubagentRecord.interruption.cause`: a cause a newer version adds reads as `"unknown"` instead of dropping the interruption, so an interrupted helper is never shown as plain cancelled.
- The ignored-spend notice (budget.run) now names every dropped key ("sets budget.run and budget.subagents.usd") and says "which does not apply from a repository" instead of "which no longer applies", since budget.subagents never applied from a repository. "--max-cost" is mentioned only when budget.run is among them.
- `projectExecutableConfig`, `repositorySubagents` and `ignoredSpendKeys` in `packages/engine/src/config/config.ts` are exported for `test/config/subagent-config.test.ts`.

## 2026-10-27 WP2 (one note pipeline)

- `NoteWindow.delay` (4.7) takes two optional inputs, `quiet` and `hold`, so `TaskNotify` can pass the `RuntimeFlags.noteQuietMs` / `noteHoldMs` overrides; without them it uses `QUIET` and `HOLD` as the contract says. The flags read `VECTOR_EXPERIMENTAL_NOTE_QUIET_MS` / `VECTOR_EXPERIMENTAL_NOTE_HOLD_MS` (positive integers; unset means the defaults).
- `TaskNotify` deps (4.7) also include `EventV2Bridge` (the `SessionStatus` service has no subscription method; the busy subscription reads `SessionStatus.Event.Status` from the bus) and `RuntimeFlags` (the overrides).
- `TaskNotify.watch` settles the child itself, exactly as `task.ts finish` did (record, budget scopes, guard release, memory hold, all under `SubagentLifecycle.controlLock`), then calls `onSettled(outcome, hold)` inside the same lock so the tool can lay the outcome over its part. The shared step is `TaskNotify.finishRun(sessions, guard, taskID, attempt, input)`, which `task.ts finish` also calls. WP3, which moves `finish` into `SubagentLifecycle`, should move `finishRun` with it.
- `TaskNotify.reports` (what a job's runs wrote) and `TaskNotify.CANCELLED_REPORT` (the old `BACKGROUND_CANCELLED`) moved with the note code; `task.ts` imports them for dependency hand-offs and the foreground cancelled result.
- "Delivering" ends once the note message has been handed to the parent (`ops.prompt` is forked into the instance scope), not when the parent's whole turn ends. Otherwise a note landing during a turn its own note started would wait for that turn to end instead of joining it, which today's 500 ms window does not do. Notes landing while a delivery waits out a revert or checks its notes are held and get a hold of their own afterwards (C.1).
- The parent's agent is no longer looked up to pass to `Truncate.output` for the 3 KB note cap: `Truncate.output` ignores that argument.
- `groups()` skips a user message whose every part carries `taskQuiet: true`: it is placed in no request, so it neither reopens a finished request nor counts as a message of one. The key is exported as `SessionTaskSize.QUIET`.
- `task.txt` rule 4 (WP9's file) said "Completion notifications are coalesced over 500 milliseconds", which WP2 makes false; it now reads "Completion notifications that land close together arrive in one message" (the A.4 wording), and `BACKGROUND_DESCRIPTION` drops its own 500 ms sentence so the rule is stated once. WP9 should keep rule 4's sentence rather than add it again.
- Permit leak found while running `test/tool/task.test.ts`: in effect 4.0.0-beta.83, `Semaphore.withPermits` takes the permit in an interruptible region, so a fiber interrupted at a scheduler yield just after taking it never releases it (seen as `metadataLock` held forever after a test's teardown, hanging every later test). Added `SubagentLifecycle.locked(lock)(effect)` (`uninterruptibleMask` around `withPermits`, the effect itself left as interruptible as the caller); `SubagentLifecycle.write` and every `TaskNotify` lock except the timer's (which must stay interruptible because `schedule` interrupts it while holding the lock) use it. Other `controlLock.withPermits` users in `task.ts` and `manager.ts` are unchanged.

## 2026-10-27 WP3 (lifecycle helpers in one place)

- `SubagentLifecycle.open` is named in WP3 but not defined anywhere in the contract. It is `open(record)`: the record's status is `queued` or `running` (the rule D.1's active board and D.3's legacy scan need). `manager.ts` keeps its two inline copies of that check; WP11/WP12, which own those paths, can switch to it.
- `INTERRUPTED_REASON`'s text is not given by the contract. It reads "Interrupted when Vector stopped (an update, restart or crash); partial work was kept." The D.3 orphan-part error is exported too, as `INTERRUPTED_ERROR = "Interrupted when Vector stopped"`.
- `claimNotification(sessions, childID, attempt, messageID)`: `attempt` is `number | undefined`, since legacy records carry none (the same rule as `write`). Because it claims only while `messageID` is unset (as WP3 says), `recover` no longer re-delivers a note whose claimed message does not exist. Before WP3 it did, which let a second recovery deliver a note again while the first claim's message was still being written; the price is that a note claimed by a prompt that then failed before writing its message is not delivered again.
- `SubagentLifecycle.finish(sessions, guard, taskID, attempt, input)` is WP2's `TaskNotify.finishRun`, moved as WP2's note asked; callers still hold `controlLock`. `task.ts` keeps a small per-call `finish` closure, because laying the outcome over that call's own part needs the call's state.
- `SubagentLifecycle.claims` is now one process-wide set instead of one per TaskTool instance. Claims are matched by parent session ID, which is unique, so the conflicts a launch sees are unchanged.
- Added `SubagentLifecycle.Claim` (the claim type) and `batchStatus(tasks)` (the batch status rule `runBatch` used, now shared with `patchEntry`).
- `patchEntry` and `settleOrphanPart` return `Effect<boolean>` (whether the part changed) and log their own failures. They write directly, without `patchPart`'s wait for a pending part, so they are for parts no live call writes. Besides the contract's running-to-error case, `settleOrphanPart` on an already settled part (a background launch) moves only that child's batch entry, or the single part's own status, from running to `cancelled` with `interrupted: true`, so its card stops showing it as running.

## 2026-10-27 Phase 1 review (WP1–WP3 fixes)

- Rejected: "settled() holds controlLock across a 10-minute patchPart poll". `onSettled` calls `persistPart`, which forks the part write in both paths (a batch through `deferred`, a single part through `forkIn(scope)`), so the lock covers only `finish`, the in-memory update and the fork. The only change is `WatchInput.onSettled`'s doc: it must not wait.
- TaskNotify's watch, timer, delivery and prompt fibers fork into the node's own layer scope. Only the windows map and its lock are instance state; the status subscription forks into the instance's cache-entry scope. A note held across a disposal is delivered from the old window, and a note enqueued after it opens a new window, so one parent can briefly have two.
- `claimNotification(sessions, childID, attempt, messageID, {stale?, note?})`: `stale` is the compare-and-set takeover; `note` is stored when the record has none, so a note enqueued without `result()` (tests, later note kinds) is still claimed. Every claim stores `notification.claimedAt`. `CLAIM_GRACE` is 60 s, and a claim without `claimedAt` (from an older engine) counts as old.
- `releaseNotifications(sessions, database, parentID, messageID, childIDs)` undoes a claim only while the parent message does not exist, so a prompt that wrote its message and then failed in its loop keeps the claim. It runs on any failure, interrupts included, for the same reason. `recover` still skips records with this process's `RUNTIME_ID`, so a note whose delivery failed is recovered after the next restart, as before WP2.
- `controlLock` is taken with `SubagentLifecycle.locked` everywhere (task.ts claim check, launch, extendRun, finish; manager.ts message, stop (both sections) and wait). The call-local part lock and the batch-local lock in task.ts are unchanged; a leak there would hang only that call.
- I19 for task routes follows 4.9: `isolation.directory` is stripped unless the principal is the owner or in control (`allowsSession`), for list, inspect, wait and stop. I19's wording ("guests never see") is stricter than 4.9 for a guest in control of its own session. WP28 or the owner should pick one rule; the handler helper is the one place to change.
- `SubagentRecord.isolation` is `Omit<Task.Isolation, "directory">` and `read()` drops a stored directory. `SubagentLifecycle.withoutDirectory` is exported for the routes. Spec 4.6 now says the part-metadata mirror carries no directory either.
- `patchPart` takes `object | ((stored) => object)` and holds `partLock` for each write. `batchEntry(metadata, index, patch)` is exported, and `patchEntry` uses it. After a batch call returns, its publish merges only its own entry.
- The ignored-spend notice stores one entry per file and key (`${repository}:${relative}#${key}`). A bare `${repository}:${relative}` entry from 1.99.111 counts as `budget.run` already noticed. The content-hash entries for folders without Git are unchanged.
- `sizing.auto` wording (finding on WP1): kept as WP1's file list requires. Spec 7.2 gains item 9, which blocks any publish from this branch before WP4–WP9 and WP30 enforce what WP1 documents.
- Removed the unused `WatchInput.callID`/`batchIndex`, `Note.hold`/`run` and `ResultInput.hold`/`format`. Spec 4.7 marks `hold` (WP16), `format` (WP19) and `run` (WP29) as landing in those WPs, and drops `callID`/`batchIndex` from `watch`, since no WP uses them.
- `docs/vector/design/subagents-v2.md` describes the per-parent window instead of the 500 ms window.

## 2026-10-27 WP4 (SpendGuard delegated ledger)

- `StopDetail.scope += "delegated"` (4.8): `StopDetail` had no `scope` field. Added `scope?: ScopeSnapshot["kind"]`; only `"delegated"` changes the wording. `afterStep(run, step, sessionID, scope?)` and `checkLimits` take it, and `apply()` passes `ledger.kind`.
- The contract gives exact text only for the delegated cap stop and the 80% note. The predicted, steps and unpriced stops got new delegated texts that name "the {cap} ceiling for this request's subagents" (or "this request's subagents used N of their M steps") and end "what it did is kept, and the main agent carries on." The loop text is unchanged: delegated ledgers run with loop rules off, so it never fires there.
- Re-arming (B.6 "stopped is cleared when spend is under the new ceiling") is precise per reason. A cap, steps or unpriced stop clears when the new budget no longer reaches it. A predicted stop clears only when the dollar ceiling rises, so the same budget, re-armed at every launch, does not reopen the ledger after each predicted stop. A loop stop is kept. Spend already past a lowered ceiling (or a seed past it after a restart) sets the stop at once, so B.2 check 3 (`delegated(ledger)?.stopped` after re-arm) refuses the launch without waiting for a step. `warned` is kept only while `usd` and `warnAt` are unchanged, so a new ceiling warns again at its own 80%.
- Lookup "by id across any lineage" uses a `delegations: id -> key` map in the service state, ordered by most recent link. `prune()` retains the last `LAST_RUNS` ids, plus an older one while a kept binding still counts on it, so a long-lived child never has its spend reset.
- A child linked with `delegated` while its root has no active run is bound with the delegated ledger as its run lineage, even when the root has a finished run (the old non-delegated rule binds to that finished run). So a resume after the root's run stopped at its cap is not stopped by it. Nested children take their parent's binding run, as before.
- Engine change outside WP4's file list: `ScopeSnapshot.kind` now includes `"delegated"`, which no longer fits `SubagentRecord.budgetScopes` (`Task.BudgetScope`, fixed kinds, I29). Added `SubagentLifecycle.scopeFields(scopes)`. It returns `budgetScopes` without the delegated scope, plus `delegatedScope` when one exists (the key is omitted otherwise, so an earlier value is not erased). `SubagentLifecycle.finish` and `TaskManager` stop write both. `TaskManager.list` shows only the filtered `budgetScopes`. This also implements B.6 "Records" for every place that persists scopes today. No engine test file was edited.

## 2026-10-27 WP5 (TaskLimits service, not yet wired)

- `seed(conversationID, requestID)` returns the spend seed `{spentUsd, steps, unpricedSteps}` instead of `void` (4.7), because B.6 has the task tool pass that seed to `guard.link({delegated: {seed}})`; it also loads the request's launch count. `admit`, `capacity` and `status` seed their key themselves before checking, so no caller has to call `seed` first. The database keeps no step counts, so `steps` seeds as 0: after a restart the request's subagent step count starts again, while spend and unpriced steps carry over.
- B.2 check 3 needs the ledger "re-armed with the current budget" before the child exists, and `link` needs a child. Added `SpendGuard.rearm(rootID, delegated)` in core (outside WP5's file list): it re-arms the delegated ledger as `link` does, or creates it at its seed, binds no session, and returns the snapshot. `admit` calls it with the conversation ID as root and the seeded spend, so the ledger exists from the first admission at the seeded amounts. The later `link` from WP6 only re-arms it, and its seed is ignored then.
- `admit`'s input gains an optional `parentID`, the launching session. A nested launch first borrows from slots its parent reserved: these are B.5's researchers using the lead's prepaid slots, which the 4.7 input could not tell apart from the pool. A `resume` whose `parentID` holds a slot (a subagent resuming its own child) is handled like a nested launch: it never waits, which avoids the B.3 deadlock.
- `status(conversationID, requestID?, limits?)` gains an optional `limits`. TaskLimits is a global node with no Config, so it shows the limits last passed to `admit`, `capacity` or `status` for that conversation. Before any of those it shows the defaults, or the guest limits for a guest-marked conversation; the FreeModelGuests dependency is there for that. WP7 should pass `resolve(config, guest)`.
- `resolve` takes `Pick<ConfigV1.Info, "budget">`, because the engine's `Config.Info` type is not exported. The engine config can be passed as it is.
- `admit` does not perform B.2 check 4 (workflow runs). Its input cannot tell a workflow-run launch from another root launch, and TaskLimits does not know which runs are running. `TaskLimits.workflowRuns(runID)` builds the exact `workflow_runs` refusal for WP31's own check.
- Workflow reserve (B.3): a workflow agent never takes a slot that would leave fewer than `min(WORKFLOW_RESERVE, running - 1)` free. Such an agent waits, which is the condition the contract names ("while any workflow launch is waiting"). Capping the reserve at `running - 1` keeps workflows runnable at `running` 1 or 2, where the literal rule would never grant a waiting agent its slot.
- The queue is strict. A head waiter that needs several slots (a research lead waiting for 1 + reserve) collects every freed slot until it fits, and nothing behind it overtakes it. Nested launches are refused while any root waiter is queued, which is B.3's rule that a free slot is promised to the queue.
- Releases follow the scope's exit. On any exit, admit's finalizer releases unbound places and reserved slots. On a failure exit it also releases the place and prepaid slots of bound children whose run never started (B.3 "a failure before start … releases it"). A nested admission's prepaid slot is also released at a successful close if its child never started: a subagent's launches always run in the foreground, so such a child never will (for example, after a failed dependency), and no slot leaks. A root launch with a reserve keeps its prepaid slots after a successful close, for a background child that starts later.
- `run` with origin `nested`, for a child that has no prepaid slot (WP7's `task_manage message` extension of a subagent's child), waits in the queue like a root launch. Nested launches never wait, because they are refused at admission, but a child launched earlier that runs again has no admission to refuse.
- `bind` finds the admission by identity (a WeakMap), so `Admission` stays exactly as in 4.7. Callers must pass the object that `admit` returned.
- Memory: idle conversations past 256, and requests past 64 per conversation, are dropped oldest first. A dropped one is counted again from the database when it is next used.
- `TaskLimits.node` is registered in `effect/app-runtime.ts` and `httpapi/server.ts` beside TaskNotify. Nothing calls the service yet.

- B.4 queued text: `{running}` is the conversation's running limit ("the most this conversation runs at once"); the admission's held count can be lower while reserved slots fill the rest. - `TaskLimits.node` is now a dependency of `ToolRegistry.node` (the task tool needs it). `FreeModelGuests` was already one.
- Existing tests changed per 5.B.3/5.B.4/5.B.8: "launches a seventeenth background subagent..." became "a ninth background subagent is queued and says how many are running or waiting" (cap 8), and the foreground busy-line test expects the new B.8 wording. The test layer adds `TaskLimits.node`, `TaskManager.node` and `FreeModelGuests.node`.

## 2026-10-27 WP7 (limits on the board, research reservation, fair batch reports)

- `research.ts` needed no change. The lead's reserve comes from `ResearchRun.brief` (`research-run.ts`), which every lead launch passes through: the research tool and a direct `task` call with `subagent_type: "research"`. `Brief.ok` gains `reserve` (the depth's `researchers` cap: 2 Focused, 4 Deep by default), and `task.ts` passes it to `admit` only when the lead's researchers stay within depth 2 (a lead launched by the root). - `TaskLimits.SLOT_REASON` (moved from `task.ts`, which re-exports it), `TaskLimits.conversationOf(sessions, root, guest)` and `TaskLimits.currentRequest(sessions, rootID)` (moved from `task.ts`) are shared so `TaskManager.list` computes the same pool and request as a launch.
- B.10: the root's board uses its latest real user message as the request. A subagent's own board uses its record's `requestID`, the request its launches count in (B.2). `list` passes `TaskLimits.resolve(current config, guest)` to `status`, so the pool's limits follow the config. An internal `collect` (the old `list`) serves `stop`, so a stop does not read limits.
- I19: the task list route drops `limits` for any principal that is not the owner ("guests never see the owner's limit values"). Checked in `test/server/auth-guest.test.ts`.
- `TaskManager.message`: an extension run waiting for a slot marks the record `queued` with `slotReason`, and its start puts it back to `running` without the reason (B.3 "lifecycle shown"). Origin comes from the record: a workflow agent is `workflow`, a child below the root's child is `nested`, otherwise `root`. - C.5: the envelope reserve is 256 bytes and 8 lines, not 6 lines. A cut entry saves the child's raw report; the output shows the neutralized text. Error entries share the budget too. - Tests outside WP7's list: `test/task/limits.test.ts` (release and the reserve clamp), `test/lib/research.ts` (TaskLimits.node in the research runtime group so a test can read the slots), `test/server/auth-guest.test.ts` (a guest's board has no limits).
- Generators: the SDK build and `packages/client` `bun run generate` produced no diff. WP1 had already added `Task.ListResult.limits` and `ExperimentalCapabilities.subagentLimits`.

## 2026-10-27 WP8 (sizing: offer rules and the request model)

- `prompt.ts` (outside WP8's file list) gains `withheldOnWork(tier, agents)`: the new `TaskSize.withheld` table plus today's "no task or task_manage below Thorough unless the user named a subagent". Both tool-filtering call sites (build and research lead) use it, so the tool set every request is sent with is unchanged until WP9 wires `offer` and flips `workDelegation` (the "behaviour behind a capability flag stays hidden" Done rule). WP9 should delete `withheldOnWork` and call `TaskSize.withheld(build.offered, agents, offer)` as A.1 says.
- The size-note texts (A.5) do change in WP8, since `note` is WP8's. Between WP8 and WP9 the Standard note says "delegate only an independent, substantial part or a broad search" while Standard still has no task tool. This build state is not publishable (release gate 7.2 item 9).
- `prompt.ts` delegation context now uses `sized.ledgerRequestID` (WP6's entry says "WP8 switches to ledgerRequestID"; WP9's file list repeats it, so that WP9 item is already done). For every request that is not a Chat message upgraded by a note, the value equals the old `carried.opened ?? users[0].id`.
- "Notes match at `id <= before`": `before` is not defined anywhere. Read as: every completion note in the request's messages up to the step being sized, the opener's own parts included, so a note `SubagentLifecycle.recover` prepends to the human opener counts. `size()` only ever sees messages up to the step, so no extra input was added.
- `notified` and the Chat rule use one predicate for a note: a `taskNotification` part whose state is not `cancelled`, without `taskNotification.quiet` and without the `taskQuiet` marker. The launching request is the one holding the last task call (`state.metadata.sessionId`, or `tasks[i].sessionId` of a batch) that launched or resumed the child before the note. A child the request launched itself counts at the request's own tier. A note whose launch is out of view (a compaction summarised it) counts as Standard.
- `ledgerRequestID` of a Chat group a note upgraded: the launching request's own `ledgerRequestID` (the highest-tier one, the latest of equals). The child's `SubagentRecord.requestID` cannot be read from the history, but it is the same value, because the launch's delegation context is that request's `ledgerRequestID`. With the launch out of view it is the previous non-Chat request's `ledgerRequestID`, else the opener.
- Chat with a note: the result's reasons become `["notified"]`, as `"escalated"` does; an escalated Chat request is checked first. The note entries of such a group take the group's tier and reasons, so the "thanks" carries the size the turn runs at. This is stable: a Chat group never runs on the build lane before the upgrade.

## 2026-10-27 WP10 (durable job rows and liveness)

- `Store.promoted(id, holder)` takes the same `{owner, attempt}` guard as `settled`. 4.8 writes it as `promoted(id)`. The extra argument lets "a stale owner or attempt is a no-op" hold for every write.
- Store writes keep their order per job. `started`, `promoted` and `cancel`'s write are forked (detached), so a slow store never delays `start`, `promote` or `cancel`. `settle` awaits its write inside the run's exit, after waking the job's waiters, so closing a registry ends only once its jobs' rows say how they stopped. Each write first waits for the job's previous write. The 2 s timeout covers that wait plus the write.
- `candidates` works out the cause instead of storing it. A running row with a dead owner is `crash`. An interrupted row is `disposed` when its owner's process is still alive (this process, or a live pid in the same boot), and `shutdown` otherwise. `disposing()` stays a boolean, as 4.8 has it. A CLI disposes its instance before it exits, and the next engine then sees a dead process, so its rows read as `shutdown`.
- `prune(before)` keeps an interrupted row until it has been reported, so a repository left unopened for more than 7 days still gets its note. It also never deletes running rows. The caller passes `now - 7 days`.
- The machine id is created under a temporary name and linked into place. A damaged file is replaced by rename. When the state folder cannot be written, the process uses an id of its own, so other engines see it as `unknown` and never act on its work. `BackgroundJobStore.useMachineFile(file)` lets tests keep the file out of the user's state folder.

- `current()` is this process's `{pid, boot, machine}`. The contract names `current` without defining it.
- Instance disposal: the `disposing(directory)` marker is set inside `InstanceRegistry.disposeInstance`, the function `InstanceStore.disposeContext` (and `reload`) call as `runDisposers`. `instance-store.ts` itself is unchanged. The marker is counted per directory, because a reload and a dispose can overlap, and it is cleared once the disposers finish.
