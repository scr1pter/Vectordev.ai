# Free models inside of Vector

This describes the free-model section and the additions prepared for desktop **1.99.111**. Vector’s service controls availability with `FREE_MODELS_ENABLED`; the desktop release does not enable it. See [Free models for Vector accounts](#free-models-for-vector-accounts).

**The free-model budget is the free path (owner decision, 17 October 2026).** In the owner's words: "i want it so that the vector app is connected to my openrouter account no matter who uses the free models". Every signed-in Vector account uses Free models inside of Vector on Vector's free-model budget, which runs on Vector's own OpenRouter account. Nothing in the free-model flow (the composer's first-run card, Getting Started, the Free models inside of Vector card, limit and unavailable messages, the TUI and the CLI) asks anyone to connect an OpenRouter account of their own; signed out, it says "Sign in to Vector to use free models." Two routes are available:

- **Free models provided by Vector.** Any signed-in Vector account, with no OpenRouter account, while Vector's service has it on. Requests pass through vectordev.ai, which checks the account and its limits. A free model chosen while an OpenRouter account was connected runs here too once that account is gone, if the shared catalog lists it.
- **Your OpenRouter account.** OpenRouter stays an ordinary provider in Settings → Providers, not promoted anywhere else. An account connected there lists its own copies of the free models under the OpenRouter provider in the picker, with that account's other models, each named "<name> (free)" (for example "Qwen3 Coder (free)"), and the composer's model button shows the same name once one is chosen. Free models inside of Vector lists only the models Vector provides. Each row's tooltip says where it runs: Provided by Vector, or Your OpenRouter account. Requests to the user's own copies go directly to OpenRouter with the stored key.

The selection decides the account: a `vector/…` model always runs on the free-model budget, even while an OpenRouter account is connected, and an `openrouter/…` model runs on that account. Pickers, the TUI and `vector models` list both copies, the shared one first. A saved, configured or recent `vector/…` choice is never moved to the user's own account, and one the shared catalog no longer lists fails as unavailable instead. Vector's own provider appears only when signed in to Vector: an OpenRouter key alone lists that account's copies, and `vector models` then still says "Sign in to Vector to use free models: run vector login." When nothing is chosen, Vector picks an own-account no-training model first, as before. Resuming after a shared limit is the one move to the user's own account, made when the user chooses it.

Names omit the `:free` suffix; routing IDs keep it. A failed catalog check never authorizes an unlisted endpoint or a paid fallback, and `max_price` stays zero on every request.

No free endpoint was marked as publishing prompts on 17 October 2026. OpenRouter's public API has no training flag; the policies come from each endpoint's `data_policy` on its model page at `https://openrouter.ai/<model id>` and the terms that endpoint links, which OpenRouter calls its best knowledge rather than a definitive source. Evidence per pair is in [free-models-legal.md](owner-actions/free-models-legal.md#evidence-per-model-17-october-2026). A model needs no entry to appear. To review one, record its evidence there, then add its pair to `REVIEWED_FREE_ENDPOINTS` with the policy found; only that can make an endpoint no-training.

Still excluded: router aliases other than the Free Models Router (`openrouter/*`), models with any price besides zero token prices (per request or per image, say), models without tools, which Vector's agent cannot work with, models whose listed modalities lack text input or give anything besides text as output, which a zero token price says nothing about, models whose every endpoint has been down all day, and anything expiring within a day. An endpoint's health counts only that way: OpenRouter's `status` is its health at the moment the catalog is read, so an endpoint down then (status other than 0) is kept if it served requests at some point in the last day (`uptime_last_1d` above zero), and the model comes back on the next refresh after a full day's outage. Until 23 October 2026 any endpoint not at status 0 when read was dropped, which hid a model for a whole day after a brief outage during the 03:17 UTC refresh; Liquid's LFM2.5-2.6B, whose one endpoint served only about a third of the day before 24 October 2026, is the likely case. A model is listed until a day before OpenRouter's `expiration_date` (the shared catalog is rebuilt daily), carries that date as `expiresAt`, and a stored catalog stops serving it once the date passes; a request for it from an out-of-date list is refused with "This model is no longer free, so Vector doesn't send it. Nothing was sent. Choose another model from Free models inside of Vector." (or, from vectordev.ai, that the model is no longer available), never sent. Poolside's Laguna models, ending 31 October 2026, are listed until the refresh of 30 October.

Of the 20 zero-price IDs OpenRouter listed on 24 October 2026 at 06:26 UTC (`packages/core/test/fixture/free-model-public-2026-10-24.json`), the shared catalog serves 16 to clients that show the label: North Mini Code, Dots3-Note Preview, Gemma 4 26B and 31B, and Xing4.0 (no training), then LFM2.5-2.6B, Nemotron 3 Nano Omni, Nemotron 3 Ultra, Nemotron 3.5 Lightning, Nemotron 3.5 Super VL, Laguna S 2.1, Laguna XS 2.1, Flint, Inkling Small and Inkling (may train), and the Free Models Router last. Gemma carries the **US only** tag; this is not a location check. Four are not offered: Google's Lyria 3 Pro and Lyria 3 Clip previews and NVIDIA's Nemotron 3.5 Content Safety, none of which lists tools, and Nemotron 3 Super, whose one endpoint served nothing that day; it returns once it does. That assumes Vector's OpenRouter account lists them all in `/models/user` ([owner steps](owner-actions/openrouter.md#free-models-of-17-october-2026-owner-steps)). On 17 October 2026 there were 19. The capture of that day (`packages/core/test/fixture/free-model-public-2026-10-17.json`) lists Lyria's token prices as zero and no other price, but no `tools` among its parameters, and its IDs are not `:free` ones; it is left out for the missing tools, not for its price or its terms. A Lyria model that listed tools would still need a `:free` ID to qualify, and OpenRouter's full listing of that day gives it audio output, which keeps it out too. Endpoints that accept tools but not `tool_choice` (Thinking Machines) are kept; an automatic tool choice is sent without the parameter.

The user's own OpenRouter key is held to the same list. Every model in OpenRouter's regular list that runs on free endpoints (`:free` variants, also with a variant after them such as `:free:nitro`, the free router `openrouter/free`, stealth models and any model listed at a zero price) is removed from it, on the legacy and V2 routes. The check looks at both the model's name and the API ID it sends, so a repository that configures one under another name (`provider.openrouter.models["alias"] = { id: "poolside/laguna-s-2.1:free" }`, or `api.id` on V2) is held to it too, and so is any provider, whatever it is called, whose base URL is on openrouter.ai or that uses OpenRouter's own SDK package. On V2, where repository configuration loads after the provider plugins, a last step removes such models again. One that reaches the engine anyway is sent only through the free-model checks, which refuse it: "This model runs on OpenRouter's free endpoints but isn't one of the Free models inside of Vector, so Vector doesn't send it. Nothing was sent. Choose a model from Free models inside of Vector." Sent as a regular OpenRouter model, it would skip the guest rule, the training notice and `data_collection: "deny"`. A router with no listed price, such as `openrouter/auto`, is not treated as free. A host written with a trailing dot (`openrouter.ai.`, also `openrouter.ai%2E`) is OpenRouter too.

A request that goes to OpenRouter as a regular model (the user's own key, on a paid model) keeps OpenRouter's model fallbacks (`models`, `route`), presets and plugins, web search included, as before. Some of these let OpenRouter answer from the endpoints of another model, which can be a free one or one whose provider may train on prompts, outside the label and the one-time acceptance. So on both engines, when a request to OpenRouter outside the free-model route sets `models` or `route`, sets `preset` or names one in its model ID (`@preset/…`), names one of OpenRouter's routers as its model (`openrouter/auto`), or sets a plugin other than web search (`web`), PDF parsing (`file-parser`) or response healing (`response-healing`), which leave the model alone, it is sent with `provider.data_collection: "deny"`, replacing whatever the configuration set there and keeping its other provider preferences. The exception is a user who has accepted the **May train on your prompts** notice, in a session no invited guest has worked in: their requests go out as configured. The check runs on the body as it is sent: on the legacy engine at the SDK's fetch, and on V2 at the transport, after the model's, its provider's, the variant's, the credential's and any plugin's body are merged, and both read the acceptance and the guest mark for each request. Provider preferences alone (`provider`, such as `data_collection` or `zdr`) only choose among the named model's endpoints and go out unchanged. On the legacy engine, `model` in a model's options replaces the model the SDK sends, so one naming a free model is still refused with the "isn't one of the Free models inside of Vector" message.

### OpenRouter's Free Models Router

`openrouter/free` is OpenRouter's Free Models Router: it is listed at a zero price and sends each request to a free model it picks at random from those that support the request's features. Vector lists it as **Auto (free)** under Free models inside of Vector, on the free-model budget and on a user's own OpenRouter account, labelled **May train on your prompts** with its own disclaimer, since the model it picks may be one whose provider trains on prompts. It goes out only after the one-time acceptance, never for a session an invited guest has worked in, and never to 1.99.108 or CLI 1.99.99 (whose catalog check would refuse it).

- A router request keeps `max_price` at zero, `require_parameters: true` and the disabled plugins, has no fallbacks (`models: ["openrouter/free"]`), and is never a fallback for another model. It cannot name providers with `only`, since the router chooses the model, so it sends `data_collection: "allow"`. While an author is barred it also sends `ignore` with that author's provider; none is barred since 23 October 2026, so it sends none, and the router may pick NVIDIA's free endpoints like any other free model. (From 17 to 23 October 2026 it sent `ignore: ["nvidia"]`; OpenRouter does not document whether a router honours that.)
- OpenRouter publishes no output limit for the router, so Vector caps its replies at 8,192 tokens, the smallest limit of any tool-capable free model on 17 October 2026 (LFM2.5-2.6B). Its context is OpenRouter's listed 200,000 tokens, though the model it picks may accept less.
- Vector never picks the router for you: every automatic choice (a new session's default, the first-run pick, the engine's and ACP's default per provider, the desktop's and TUI's fallback to a provider's first model) skips it, even when it is a provider's only model, and the shared catalog lists it last.

**Answers-only models.** No free model without tools is offered. On 24 October 2026 the only zero-price ones are NVIDIA's content-safety classifier and Google's two Lyria music previews. Whether the agent loop should offer a model that cannot edit files or run commands is an open owner question.

### The label, the disclaimer and the one-time consent

- Wherever a may-train model is listed, one Vector has not reviewed included, it says **May train on your prompts**, and nothing else: the desktop picker row, its tooltip and spoken label, the composer's model chip tooltip, the TUI model list, and the `vector models` caption on stderr. NVIDIA's models carry no extra notice. The desktop picker, the TUI and `vector models` list no-training models first, then the labelled ones, and the Free Models Router last.
- The disclaimer: "This free model's provider may log your prompts, code and outputs and use them to train its models. Vector itself never trains on your prompts. Don't use it with private repositories, secrets or personal data." The acceptance question adds that it covers models Vector has not reviewed yet.
- Model lists and in-use notices show the short label. The disclaimer belongs to the one-time consent question; no-training, paid and other providers' models show neither.
- Before the first prompt to such a model, the desktop asks once (**Accept and send** or **Don't send**), and the TUI asks when the model is chosen. The draft stays in the editor if the user declines. The question names the chosen model and says that accepting covers every model labelled **May train on your prompts**, including ones Vector has not reviewed yet, now and later, until it is withdrawn. The acceptance is recorded by the engine in `~/.local/state/vector/free-model-training-consent.json`, a fixed path under the home directory, so the desktop engine (whose XDG directories sit inside the app's data folder), the TUI and the CLI on one computer share it and read it on every request. An engine on another computer, such as `vector serve` on a server, keeps its own.
- The engine refuses to build a request to such a model without that record, so nothing is sent from any client, including `vector run`, subagents and reviews. The refusal says: "... Nothing was sent. Accept it once when Vector asks, or run "vector models --accept-training", then send again." **Withdraw** on the Free models inside of Vector card in the desktop Help panel, or `vector models --decline-training`, withdraws it.
- An invited guest (`vector invite`) runs on the owner's engine, under the owner's acceptance, which the guest never gave. So a guest is not offered models labelled **May train on your prompts** (the provider list leaves them out and the consent read says no), and the engine refuses a guest's prompt (including a subtask part that names one), compaction, worker message, model switch or free-model resume that would run on one, on the legacy and V2 routes, before anything is saved: "Only the workspace owner can use free models labelled "May train on your prompts" here, since only they can accept that notice. Choose another model." The same text replaces "try again" when an acceptance is refused with 403.
- The guest's input stays in the session's history and goes out again with every later request there, so the rule also holds where each free-model request is built (`FreeModels.resolveRoute`, used by the legacy fetch and the V2 runner alike). Once a guest has sent a session any request other than a read (GET or HEAD), or answered one of its questions, the whole session tree (its subagents and its parent) is marked in `FreeModelGuests`, and no request for it goes to a labelled model, the owner's own prompts, compactions, titles, summaries, subagents, retries and fallbacks included: "An invited guest has worked in this session, and only the workspace owner can accept the "May train on your prompts" notice, so Vector doesn't send this session to free models with that label. Nothing was sent. Choose another model." Marks are kept beside the database (`free-model-guest-sessions.txt`, one session per line, appended so two engines marking at once both keep their marks), so a restart does not clear them, and a fork of a marked session, which copies the guest's messages, is marked too. A guest request forwarded to a remote workspace reaches that workspace's engine with the owner's credentials, so it carries `x-vector-guest-request: 1`, and that engine marks the session the same way, for prompts and for answers to questions. The forwarding engine marks the session too, and warping a marked session into a remote workspace sends the same header with the steal, so the mark follows the session between engines. A session imported from an archive, or warped back from a remote engine where a guest worked in it directly, starts unmarked. The remote engine's early refusals still see an owner there, so a forwarded guest prompt to a labelled model is refused when it is sent, not before it is saved.
- Vector never chooses a may-train model for you ahead of a no-training one.
- Vector itself never trains on prompts. That is a statement about Vector, not about the providers.

### Old clients keep a no-training catalog

Desktop 1.99.108 and CLI 1.99.99 never show the label, so vectordev.ai serves may-train models only to clients that declare they show it: `GET /api/free-models/models?disclosure=may-train-v1`, and the header `x-vector-free-model-disclosure: may-train-v1` on shared chats. Any other client receives the no-training models only, and its shared chats fall back only among them. The shared chat refuses a may-train model with 403 `FREE_MODELS_DISCLOSURE_REQUIRED` when the disclosure is missing and 403 `FREE_MODELS_CONSENT_REQUIRED` without `x-vector-free-model-training-consent: accepted`, before any budget is spent.

## Limits, and what Vector says at one

The free-model budget runs on Vector's OpenRouter account, which has bought $10 of credits (owner, 17 October 2026). OpenRouter sets the free tier by credits purchased over the account's life, so the account gets **1,000 free-model requests a day** instead of 50, and keeps it as the balance is spent; OpenRouter states no expiry. The limit is still **20 requests a minute**, counted across all the account's keys, so every user of the free-model budget shares both. Failed attempts count, and one coding task can use many requests, since each tool step is one. See [OpenRouter's current limits](https://openrouter.ai/docs/api_reference/limits).

At a limit, Vector says what happened, when the free-model budget is expected to reset, and what else to do, never connecting OpenRouter: "To keep working now, choose a model from another provider you've connected, or add your own provider key in Settings → Providers." The TUI and CLI say `/connect` or `vector providers login` instead of Settings. A user who already connected OpenRouter can still continue the same turn on it. Vector never switches to a paid model or provider. Desktop 1.99.108 and CLI 1.99.99 write their own limit text from the typed limit, which still mentions OpenRouter; only a new release changes that.

**Never let the shared account's balance go negative.** OpenRouter refuses free models with HTTP 402 on an account with a negative balance, which takes the whole free-model budget down (Vector shows it as "Shared free models are temporarily unavailable"). Every shared request sends a zero `max_price` and disables paid plugins, and every one but the Free Models Router's names only zero-price endpoints, so free use does not spend the credits; keep automatic top-ups, paid upstream BYOK keys and default or enforced paid plugins off on that account, and use it for nothing else.

A personal OpenRouter account connected in Settings → Providers has its own limits: 50 free-model requests a day without a credit purchase. Keep it free of purchased credits, payment methods, automatic top-ups, paid BYOK keys and paid plugins if it should cost nothing; those settings are outside Vector's control.

## Your OpenRouter account's privacy settings

OpenRouter has separate privacy settings for free and paid models. If a user's account does not allow free models from providers that may train on their data, OpenRouter does not list those models for that account, so they do not appear under **Your OpenRouter account**. When such a model was chosen from the free-model budget, or OpenRouter answers that no endpoint matches the data policy for a may-train model, Vector says: "Your OpenRouter privacy settings block free models whose providers may train on prompts. To use this one, open openrouter.ai/settings/privacy, allow free models from providers that may train on your data, then send again. Or choose a model without the "May train on your prompts" label." The same applies to a model Vector has not reviewed, which is sent `data_collection: "allow"` after the acceptance like any may-train model. (Before 23 October 2026 such a model was sent `data_collection: "deny"`, and Vector said it had found no provider of it that doesn't train.)

## Start free

In the desktop app, the composer's card (shown while no connected provider offers a model) says "Sign in to Vector to use free models." and offers **Sign in to Vector** and **Use my own API key**; **Start free** in Getting Started starts the same sign-in. Once signed in, the shared models load, the card goes away and the composer selects a free model, a no-training one first; the draft prompt stays ready to send. If the free-model budget serves nothing while you are signed in, the card says Free models inside of Vector are unavailable right now and offers your own API key. The web build, which cannot sign in itself, says instead: "To use free models, sign in to Vector on the computer this page connects to: run vector login there, then restart Vector. Or use an API key you already have.", and offers the key only. In the terminal, the TUI home screen says "Sign in to Vector to use free models: run vector login." while the shared catalog is on, or that the free models are unavailable right now, and offers `/connect` for your own key. Signed out while the shared catalog is on, `vector models` prints the same line on stderr, and `vector run` adds it to its message that no model provider is connected:

```sh
vector login
vector models
vector models --accept-training   # only if you want models labelled "May train on your prompts"
```

`vector models` keeps canonical `provider/model` selectors on stdout. Its free-model heading, display names, source captions, labels and the disclaimer go to stderr.

**Your own OpenRouter account.** Settings → Providers → OpenRouter connects one through browser authorization (its callback is on the engine's localhost, so a remote engine needs an API key) or an API key; `OPENROUTER_API_KEY` in the engine's environment works too. A key only in a repository's `provider.openrouter.options.apiKey` does not list its free models.

## Free models for Vector accounts

`FREE_MODELS_ENABLED=false` keeps the free-model budget off without disabling a personal OpenRouter connection. A model chosen under the user's own OpenRouter account keeps running there; a shared choice does not move to it.

The daily refresh (03:17 UTC, `/api/free-models/refresh`) reads OpenRouter's public `/api/v1/models`, Vector's account list `/api/v1/models/user` (which applies that account's privacy settings and provider preferences), and, for each candidate, `/api/v1/models/{author}/{slug}/endpoints`. Every offered free model is a candidate, reviewed or not. It keeps zero-price, tool-capable endpoints that are up or served requests in the last day, of models more than a day from expiry, each with its reviewed policy or may-train, plus the Free Models Router, which lists no endpoints and is judged by its own listing. Endpoint lists are read five at a time. It logs, by model ID, the offered free models the account's own list leaves out (only the account's settings on openrouter.ai can change that), the ones with no usable endpoint, and the ones whose endpoint list could not be read. One unreadable endpoint list drops only that model; a failed model or account list keeps the stored catalog, and so does a run in which endpoint lists failed and no model with endpoints of its own was left, such as an OpenRouter outage or rate limit during the cron: it answers 503 `FREE_MODELS_CATALOG_UNAVAILABLE` instead of publishing `enabled: false`. When every list was read and no model with endpoints of its own qualifies, it publishes `enabled: false`: the Free Models Router alone never keeps the section on, and a stored catalog holding only the router is served as off to every client. The catalog is stored under `vector:free-models:catalog:v4:policy` for 54 hours, so one failed nightly run does not take the section down. Every stored endpoint must carry the policy today's rules give it, the reviewed one or may-train, or the whole catalog is refused as `FREE_MODELS_CATALOG_INVALID`; a stored no-training endpoint the record does not know fails, and so does an `unreviewed` one. A catalog stored before 23 October 2026 passes, so the key did not change; after a rollback to a build from before that day, run the refresh, because the older check refuses a catalog holding unreviewed or NVIDIA endpoints.

`/api/free-models/models` returns a 503 whose code says why: `FREE_MODELS_CATALOG_MISSING` (never refreshed under the current key), `FREE_MODELS_CATALOG_STALE`, `FREE_MODELS_CATALOG_INVALID` or `PERSISTENT_STORE_UNAVAILABLE`.

For hosted activation, set the Vector account/token and persistent Redis configuration, `OPENROUTER_FREE_API_KEY`, `CRON_SECRET` and `FREE_MODELS_ENABLED=true` on the server, then run the refresh; see [owner actions](owner-actions/openrouter.md#free-models-of-17-october-2026-owner-steps). `FREE_MODELS_MINUTE_PER_USER` defaults to 10 (at most 20) and `FREE_MODELS_DAILY_PER_USER` to the smaller of 20 and a tenth of the account's daily free limit (at most 1,000). With the account's 1,000 a day, set `FREE_MODELS_DAILY_PER_USER=50`: enough for a few agent tasks a day, while 20 users at that rate reach the account's limit, after which everyone sees "Free tokens have run out for today" until the next UTC day. These settings do not raise OpenRouter's account-wide quota, which every user of the free-model budget shares.

## Clients after an outage

A client caches the catalog in `free-models-v2.json`. When vectordev.ai answers with a refusal such as 503, the client treats the shared catalog as off instead of listing models whose prompts would fail. A network failure keeps the last catalog it served. When the catalog later turns on, the engine rebuilds its provider list without a restart.

Prompts pass through OpenRouter and the selected provider. Vector does not request zero data retention for these endpoints. Most keep prompts under their own policy; OpenRouter records Phala's Xing4.0 endpoint as keeping none. The routing rules cover the model requests only, not Vector's local history, OpenRouter account logging or other connected services.
