# Vector service independence — upcoming release candidate

**Unversioned source candidate.** No release date or new version is assigned here. These notes describe the cumulative implementation of Part 1 and Parts 2.1–2.28, including features prepared behind disabled switches. They do not announce a production service, npm publication, installer, signed update feed or replacement Mac app. Final cumulative acceptance and publication evidence belong to the release coordinator. Pricing, subscriptions and HULK behavior are unchanged.

## Public release note

The candidate restores a path to Free models inside of Vector through OpenRouter, consent-based public sessions on Vector's own service, native installers, WSL account handoff and team configuration. It also improves upgrade recovery, provider adapters, crash reports and web fetch. Shared model access remains disabled until the owner completes its service and privacy setup. Provider sign-ins that require registrations remain disabled; API-key connections continue to work. The public SDK and container distribution are prepared, with publication still pending.

## Part 1: Free models inside of Vector

A live Vector catalog selects reviewed, zero-price, tool-capable OpenRouter endpoints. Both session engines, review, GitHub tasks, ACP and small-model work use the same routing rules. When the service is enabled and the user is eligible, a fresh session can use a free model without a provider key. When it is OFF or unavailable, clients show provider setup instead of promising model access. The ordinary bundled catalog describes models; it does not grant access.

The shared route authenticates the Vector account, sends a hashed user identity and fixes the upstream destination. It enforces zero-price ceilings, provider/privacy restrictions, bounded streaming, fair-use reservations, daily/minute limits and cancellation. It cannot choose a paid fallback. Shared requests are checked against the 4.5 MB UTF-8 ceiling before network transport. Optional cache writes cannot discard an already validated in-memory catalog or OFF result.

Connect OpenRouter uses the user's own authorization and takes precedence over the shared allowance. A typed limit message carries reset/retry information and offers connection from desktop and TUI. After authorization the same conversation resumes without duplicating the admitted prompt or completed tool calls. Free-model titles and compaction do not silently choose a paid model. The desktop account exchange and standalone CLI use their respective protected stores; credentials are not made universally readable across processes.

`FREE_MODELS_ENABLED` stays OFF by default. The owner must complete OpenRouter account, terms/privacy, key, persistent KV, allowance and live availability checks before enabling it. Synthetic source and compiled acceptance prove implementation behavior, not owner-key access or approval. See [OpenRouter setup](owner-actions/openrouter.md), [privacy review](owner-actions/free-models-legal.md) and [desktop/CLI vault decision](owner-actions/desktop-cli-vault.md).

## Parts 2.9–2.10: public sessions and historical links

Vector-owned sharing is implemented in both engines and the App, TUI and CLI. A read-only preview shows the visible transcript before publication. Sharing requires explicit account-bound consent, an expiry of at most 30 days and a choice about future updates. Project `share`/`autoshare` settings do not independently authorize upload; remembered consent is a separate trusted local choice. GitHub sharing defaults off and requires its current consent acknowledgement.

The normalized public archive contains visible prompts, answers, reasoning and tool display data. It excludes hidden system context, application state and management secrets, but visible code and tool output can still contain sensitive material. Attachments are descriptive labels; viewers/importers do not fetch local files or arbitrary attachment URLs. Snapshot-only publication checks the reviewed preview hash. Updates use revision checks and retries; lost acknowledgements cannot publish an unreviewed replacement snapshot or leave a permanently stale hash.

POST/PUT/DELETE use Vector account authorization and privately held management secrets. Public GET stops serving removed or expired data immediately. Permanent minimal tombstones prevent delayed creates from resurrecting deleted links. Live payloads are erased on unshare/account deletion; expiry cleanup is bounded and backup retention requires owner review. Local publication rows and durable share events remain separate from historical URLs.

`vector run --share`, TUI `/share` and `/unshare`, URL import and PR-linked imports are restored for the new service. Full-fidelity local exports remain available. Public imports use fresh IDs, validate before a transaction and create passive history: they never execute imported tool calls or admit a prompt. Portable public transcripts can target the active engine; native full-fidelity archives stay native. The legacy CLI cannot continue a full native archive as a legacy session.

Part 2.10 remains an owner choice between a one-time user-started removal action and retained-link removal instructions. Neither option is silently selected. Old public links and secrets remain available on failed removal. Local deletion warns about retained links, including descendants, and explicit local-only confirmation never claims remote deletion. A new Vector unshare cannot remove a historical copy on another service. See [new share setup/privacy](owner-actions/public-shares.md) and [historical share options](owner-actions/old-public-shares.md).

## Parts 2.11–2.16: distribution and integrations

**2.11 Native installers.** POSIX and PowerShell installers use the fixed Vector release API and immutable per-platform archives, without Node/npm. They verify metadata, size, SHA-256, exact archive entries and the staged binary's version. Receipts bind ownership; unrelated executables, links and metadata are refused. Updates stage on the same filesystem and preserve recovery backups if rollback fails. Windows replacement/removal waits for the exact running parent to exit and reports scheduled status until completion. `vector upgrade` and `vector uninstall` follow verified standalone or package-manager ownership. Homebrew/Scoop definitions are generated for owner-provided repositories; coordinates are not guessed. The standalone entrypoint retains the existing Vector account requirement. See [distribution setup](owner-actions/standalone-cli-release.md).

**2.12 WSL.** The desktop pins its required CLI version independently of the app version and installs it through the exact-version native installer as `~/.vector/bin/vector-native`. Installation needs Linux download/archive/hash tools, not Node/npm. The dedicated historical WSL binary can migrate through a verified private staging transaction. The desktop account token is passed only through the managed process's stdin, not command arguments or a new credential file. Rotation/logout stop stale generations and their Linux descendants before success; inability to confirm termination is an error. Startup preserves loopback binding and the unauthenticated HTTP 401 check. Actual Windows/WSL execution remains a platform release check.

**2.13 GitHub App.** A Vector-owned App/OIDC token exchange and installation verification flow are prepared. `GITHUB_TOKEN` remains the default; App/auto is explicit. The server verifies trusted workflow/job/repository identity and issues repository-scoped tokens. Fork PR code cannot run with App credentials. Git network child processes receive credentials only for the verified repository, with hooks and other untrusted execution paths disabled; model tools do not inherit them. Tokens are revoked on completion/cancellation. The owner registers/configures the App before enabling it. See [GitHub App setup](owner-actions/github-app.md).

**2.14 GitLab Duo.** Both engines implement a bounded device grant and refresh with client/issuer binding and final endpoint checks. The existing desktop registration is only a candidate pending ownership and Duo-use confirmation. The gate remains false; API/PAT access continues. The installed SDK's Vector cache/guidance rewrite and cleared inherited registration remain enforced. See [GitLab setup](owner-actions/gitlab.md).

**2.15 Bundled providers.** Reviewed adapters for Cloudflare AI Gateway, SAP AI Core, AIHubMix, Merge Gateway, IBM watsonx and external-server QVAC are bundled and lazily loaded in both engines. They do not install these SDKs at runtime. SAP uses per-instance credentials; IBM token errors are bounded/redacted; AIHubMix omits publisher referral metadata unless explicitly supplied. Salad Cloud is removed from the advertised allowlist because its SDK requires an incompatible major runtime. No managed QVAC runtime is downloaded. License/advisory checks and compiled SDK wire fixtures accompany the adapters. A new public catalog still requires reviewed publication. See [provider setup](provider-sdks.md).

**2.16 Crash reports.** Terminal, desktop and browser crash actions create editable drafts for Vector's support flow. Stack traces do not travel in URLs or send automatically. Loopback transfer is scoped, bounded and short-lived; submission failures preserve the draft. The Help menu points to the public support form.

## Parts 2.23–2.28: teams, SDK and supporting surfaces

**2.23 Vector Teams.** A private Supabase membership/configuration store and signed HTTPS configuration service are prepared. Ed25519 payloads bind the account credential, membership, selected team, revision and a lifetime of at most 15 minutes. Clients fetch verification keys only from Vector, reject stale/tampered/account-mismatched policy and fail closed for a selected unavailable team. Personal mode needs no startup request and can clear corrupt selection offline. Desktop, TUI and CLI offer explicit switching; both engines invalidate cached configuration. Team defaults merge before local settings and are not an immutable device-management policy. The owner provisions the database/signing key and enables the service; no public membership-admin UI is claimed. See [Teams setup](owner-actions/teams.md).

**2.24 Public SDK.** `@vectordevai/sdk` staging, explicit publication tooling and clean npm consumer checks are prepared. Generated clients document `vector serve`; package exports, declarations, HTTP calls and child-process cleanup are tested outside workspace links. First publication, package version and distribution-license approval remain owner actions. The source workspace's private flag is not a claim that a public package exists. See [SDK setup](owner-actions/npm-sdk.md).

**2.25 Container.** Native x64/arm64 container jobs consume verified musl release archives, carry notices and run as a non-root user. Publication uses an explicitly configured GHCR owner and short-lived workflow credentials; different existing version tags cannot be overwritten. A multi-platform index follows successful architecture jobs. No moving latest tag, registry creation or actual Docker runtime acceptance is claimed. See [registry setup](owner-actions/container-registry.md).

**2.26 Build dependencies.** The used documentation theme is vendored locally with its complete MIT notice and integrity provenance. The existing pinned OpenTUI packages remain; the separately documented Vector fork is an owner choice and has not been started. See [OpenTUI options](owner-actions/opentui.md).

**2.27 Web fetch.** Both engines use a browser-like user agent ending in Vector/version and retry one declared Cloudflare challenge with Vector identity. Ordinary HTTP errors are not retried. The challenge body is aborted before retry, both attempts share the deadline, and response collection is bounded. This does not guarantee access to every website.

**2.28 Social cards.** An optional `/api/og?title=…` renderer supplies per-page images with bundled assets, bounded title input and persistent rate protection. The static logo remains the default unless `VECTOR_OG_ENABLED=true` is set for the website build and server. No arbitrary asset fetch or dynamic service enablement is implied by these notes.

## Verification and remaining release decisions

Part 1's recorded checkpoint passed all 21 package typechecks, 1,252 App tests and source/compiled free-model recovery fixtures. Its full Engine result was 3,551 passes with two documented baseline failures, not an all-green result. Later sharing, GitHub, provider, Teams, installer and browser fixtures have their own source/compiled scope. These checkpoints are not a substitute for the coordinator's final cumulative run and per-platform artifact inspection.

The strict binary-name check remains unresolved: the earlier audited development binary retained required notices and identified Monaco/Bun internal identifiers. No byte patching or encoded concealment was used. Source guards and absence of retired hosts/credentials do not equal zero binary matches. See [binary identifier decision](owner-actions/binary-identifiers.md).

Before a public release: finish cumulative checks; choose the release version; resolve legal/privacy and first package-publication approvals; provision only the owner-approved services; publish/verify catalog, plugin, SDK and CLI artifacts in dependency order; run actual Windows installers/WSL and native containers; sign/notarize desktop packages; verify immutable manifests and update feeds; then deploy and probe both websites. GitHub's recorded billing/spending block is an external prerequisite for blocked jobs, not a passing result. Unsigned review artifacts do not advance signed update feeds. No new app installation or production deployment is claimed in this draft.
